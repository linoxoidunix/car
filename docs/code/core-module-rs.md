# 5. `crates/cra-core/src/module.rs` — декомпозиция Дютюи–Рози

**Размер:** 162 строки. **Задача:** найти в схеме независимые куски, чтобы
каждый можно было решить отдельно.

Это самый важный для производительности файл движка. Именно он превращает
схему из 15 000 событий из «невозможно» в «шесть секунд».

## Какую задачу решает

Вернёмся к насосной станции: `(A И B) ИЛИ V`.

Элемент `И(A, B)` использует события A и B, и **больше их нигде нет**. Значит,
его можно посчитать полностью отдельно:

```
P(И(A,B)) = 0,1 × 0,1 = 0,01
```

а потом заменить весь этот кусок схемы **одним псевдособытием M** с
вероятностью 0,01. Вершина превращается в `M ИЛИ V` — задачу с двумя
переменными вместо трёх.

```
   ИЛИ                 ИЛИ
   ├── И          →    ├── M   (P = 0,01, посчитан отдельно)
   │   ├── A           └── V
   │   └── B
   └── V
```

На трёх событиях выигрыш незаметен. На 15 000 событий и 8 000 элементов
разница между «одна булева функция от 15 000 переменных» (невозможно) и «сотни
функций от десятка переменных каждая» (мгновенно) — это разница между рабочим
инструментом и неработающим.

Такой независимый кусок называется **модулем**.

## Определение модуля

> Модуль — это логический элемент, ни один потомок которого не используется
> нигде за пределами этого элемента.

Или, житейски: поддерево, у которого нет «утечек» наружу.

**Контрпример.** Возьмём `(A И B) ИЛИ (B И C)`. Здесь `B` встречается в обеих
ветвях. Ни `И(A,B)`, ни `И(B,C)` модулями не являются: обе ветви зависят от
одного и того же события, и перемножать их вероятности нельзя.

Проверим ошибку численно, при q = 0,1 у каждого:

```
неверно (как будто независимы): 1 − (1 − 0,01)(1 − 0,01) = 0,0199
верно (точно):                  P(AB) + P(BC) − P(ABC)
                                = 0,01 + 0,01 − 0,001    = 0,019
```

Разница в полпроцента здесь выглядит мелочью, но в реальных схемах с сильным
переиспользованием элементов такие ошибки накапливаются и систематически
завышают вероятность. Поэтому строгое определение модуля критично: движок
раскладывает на модули **только там, где независимость действительно есть**, а
всё остальное отдаёт BDD, который справляется с общими переменными точно.

## Алгоритм: два обхода в глубину и три числа

Наивная проверка «есть ли у этого элемента потомок, используемый снаружи?» для
каждого элемента стоила бы O(n²). Алгоритм Дютюи–Рози делает это за **линейное
время** — один проход, что бы ни было в схеме.

### Ключевая мысль

Обойдём граф в глубину (DFS), ведя часы, которые тикают на каждом шаге. Для
каждого узла запомним:

- `d1[v]` — момент **первого** посещения;
- `dl[v]` — момент **последнего** посещения.

DFS входит в поддерево элемента `v` и выходит из него; всё это время часы
идут. Получается «временно́е окно» `[d1[v], dl[v]]`, соответствующее визиту в
поддерево.

Теперь: если у некоторого потомка `c` есть *другой* родитель за пределами
поддерева `v`, то DFS посетит `c` ещё раз — вне окна `v`. Значит, либо
`d1[c] < d1[v]` (его увидели раньше, до входа в `v`), либо `dl[c] > dl[v]`
(его увидели позже, после выхода из `v`).

Отсюда критерий:

```
v — модуль  ⟺  min(время первого посещения потомков) > d1[v]
                и  max(время последнего посещения потомков) < dl[v]
```

Ни один потомок не выглядывает за окно — значит, ни у одного из них нет связей
наружу.

### Шаг 1 — расставить времена

```rust
let mut d1 = vec![0usize; n];   // 0 значит «ещё не посещали»
let mut dl = vec![0usize; n];
let mut t: usize = 0;           // часы
let mut stack: Vec<(NodeId, usize)> = Vec::new();
```

Обход написан **со своим стеком, а не рекурсией**. Причина практическая: схема
может иметь глубину в тысячи уровней, а рекурсия на такой глубине переполнит
стек потока и уронит процесс. Собственный стек живёт в куче и ограничен только
объёмом памяти.

Каждый элемент стека — пара `(узел, номер следующего ребёнка)`; так вручную
эмулируется «вернуться и продолжить с того места, где остановились»:

```rust
while let Some((v, ci)) = stack.pop() {
    if ci < f.child_count(v) {
        stack.push((v, ci + 1));      // вернуться позже за следующим ребёнком
        let c = f.child_at(v, ci);
        t += 1;
        if d1[c] == 0 {
            d1[c] = t; dl[c] = t;
            stack.push((c, 0));       // первый раз видим — заходим внутрь
        } else {
            dl[c] = t;                // видели раньше — обновляем только «последний раз»
        }
    } else {
        t += 1;
        dl[v] = t;                    // все дети обработаны
    }
}
```

Существенно, что при повторной встрече узла мы **не заходим внутрь снова** (это
дало бы экспоненциальный обход ДАГа), но `dl` всё равно обновляем — а именно
это обновление и «выдаёт» узел, используемый в нескольких местах.

### Шаг 2 — свернуть по потомкам снизу вверх

```rust
let mut minf = vec![usize::MAX; n];  // min времени первого посещения потомков
let mut maxl = vec![0usize; n];      // max времени последнего посещения потомков
```

Второй обход в глубину, снова со своим стеком, вычисляет для каждого узла
минимум и максимум по всем его потомкам. Массив `state` (0 = не видели,
1 = на стеке, 2 = готов) не даёт обработать узел дважды:

```rust
mn = mn.min(d1[c]).min(minf[c]);   // сам ребёнок и всё его поддерево
mx = mx.max(dl[c]).max(maxl[c]);
```

Так как значения ребёнка уже готовы к моменту обработки родителя, каждый узел
трогается ровно один раз. Отсюда линейное время.

### Шаг 3 — применить критерий

```rust
for v in 0..n {
    if v == root || d1[v] == 0 || !f.is_gate(v) { continue; }
    if minf[v] > d1[v] && maxl[v] < dl[v] {
        result.insert(v);
    }
}
```

Пропускаются: корень (он добавлен заранее — вся схема всегда модуль),
непосещённые узлы (`d1 == 0` — мусор, не связанный с вершиной) и листья
(отдельное базовое событие модулем не считают, оно и так атомарно).

## Тесты — три случая, которые всё объясняют

Тесты в конце файла и есть лучшая документация к алгоритму.

### `independent_subtrees_are_modules`

```
(a & b) | (c & d)
```

Два элемента И используют разные события. Модулями являются **оба**, плюс
вершина. Итого 3. Это идеальный случай: схема разваливается на три
крошечные независимые задачи.

### `shared_event_blocks_modules`

```
(a & b) | (b & c)
```

Событие `b` общее. Модулем является **только вершина**, ответ `m.len() == 1`.
Алгоритм корректно отказывается разбивать то, что разбивать нельзя, и вершину
целиком отдают BDD — который посчитает 0,019 точно.

### `shared_gate_with_private_subtree_is_module`

Самый тонкий случай:

```
m_gate = p & q
g      = x & m_gate
top    = m_gate | g
```

У `m_gate` **два родителя** — он используется дважды. Но его собственное
поддерево (`p` и `q`) больше нигде не встречается. Поэтому `m_gate` — модуль!

Это важно и часто неверно понимается: модульность определяется не числом
родителей, а тем, «утекают» ли потомки наружу. `m_gate` можно посчитать один
раз, а результат подставить в оба места как одну переменную. Именно это и
делает `analysis.rs` через мемоизацию в `done: HashMap<NodeId, usize>`.

## Как результат используется дальше

`find_modules` возвращает `HashSet<NodeId>` — множество идентификаторов
элементов, являющихся модулями. Дальше `analysis.rs`:

1. начинает с корня;
2. обходит его поддерево, но **останавливается** на каждом вложенном модуле,
   заменяя его на переменную-псевдособытие;
3. рекурсивно обрабатывает каждый вложенный модуль тем же способом;
4. строит по одному BDD на модуль и собирает вероятности снизу вверх.

Вероятность верхнего события при этом остаётся **точной**: модули по построению
статистически независимы, поэтому подстановка вероятности модуля вместо
переменной — не приближение, а тождество. Тест
`modular_decomposition_is_exact` в `tests/integration.rs` проверяет это с
точностью `1e-15`.
