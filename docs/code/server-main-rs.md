# 11. `crates/cra-server/src/main.rs` — точка входа службы

**Размер:** 59 строк. **Задача:** объявить модули сервера, прочитать
настройки, запустить приём связей.

## Какую задачу решает

CLI годится для одного инженера за своей машиной. Для общего сервера, к
которому подключаются тонкие клиенты, нужна служба:

- расчёт идёт на мощном сервере, у клиента только браузер;
- модель не расходится по флешкам, а живёт в одном месте;
- все обращения записываются в журнал (требование аттестованных систем);
- обновление — замена одного файла.

Этот файл — три десятка строк, соединяющих остальные семь.

## Объявление модулей

```rust
mod assets;    // встроенные файлы веб-интерфейса
mod audit;     // журнал безопасности
mod auth;      // аутентификация
mod config;    // настройки из окружения
mod handlers;  // маршрутизация и обработчики
mod http;      // разбор HTTP/1.1
mod server;    // приём связей, пул потоков
```

Здесь `mod`, а не `pub mod`, как в [`lib.rs`](core-lib-rs.md) движка: это
исполняемая программа, у неё нет внешних пользователей, и всё остаётся
внутренним.

## `main`

```rust
fn main() {
    if std::env::args().any(|a| a == "-h" || a == "--help") {
        print_help();
        return;
    }
    let cfg = match Config::from_env() {
        Ok(c) => c,
        Err(e) => { eprintln!("configuration error: {e}"); std::process::exit(2); }
    };
    if let Err(e) = server::serve(cfg) {
        eprintln!("fatal: {e}"); std::process::exit(1);
    }
}
```

Существенная деталь — **порядок**: настройки читаются и проверяются **до**
того, как открыт сокет. Опечатка в переменной окружения приводит к
немедленному выходу с кодом 2, а не к службе, которая вроде бы работает, но с
неверными параметрами безопасности.

Это важно именно для systemd: юнит с `Restart=on-failure` будет перезапускать
процесс, и мгновенное падение с внятным сообщением в журнале — то, что нужно.
Служба, молча стартовавшая с `CRA_AUTH=none` вместо задуманного
`CRA_AUTH=proxy`, была бы гораздо хуже.

Коды возврата те же, что у CLI: 2 — ошибка конфигурации, 1 — ошибка
выполнения.

## `print_help` — единственная документация по эксплуатации

```
CRA_ADDR            bind address           (default 127.0.0.1:8080)
CRA_WORKERS         worker threads         (default = CPU count)
CRA_MAX_CONN        max concurrent conns   (default 256)
CRA_TIMEOUT_SECS    per-request timeout    (default 120, 0 = off)
CRA_AUTH            none | token | proxy   (default none)
CRA_TOKEN           bearer token           (required if AUTH=token)
CRA_PROXY_HEADER    identity header        (default X-Remote-User)
CRA_TRUSTED_PROXIES trusted proxy IPs (default 127.0.0.1,::1)
```

Плюс список endpoint'ов и предупреждение:

> Deploy behind a certified ГОСТ-TLS proxy; do not expose plain HTTP outside a
> trusted network segment.

Справка выводится в **stderr**, а не в stdout. Соглашение спорное, но здесь
последовательное: stdout у этой программы не используется вовсе, весь
диагностический вывод (включая журнал аудита) идёт в stderr, откуда его
забирает journald.

## Почему нет TLS

Сказано в шапке файла:

> TLS здесь нет by design: ставьте впереди сертифицированный ГОСТ-TLS прокси.

Это не упущение, а архитектурное решение, и у него две причины.

**Юридическая.** В аттестованной системе шифрование обязано выполняться
сертифицированным СКЗИ (КриптоПро и т. п.). Приложение, реализующее TLS само,
претендовало бы на роль средства защиты — и попало бы под сертификацию
целиком. Отдав TLS внешнему nginx/Angie с ГОСТ-криптографией, приложение
остаётся обычной прикладной программой.

**Инженерная.** TLS-стек — это десятки тысяч строк чужого кода и постоянный
поток уязвимостей. Весь этот сервер — примерно 700 строк, которые можно
прочитать за час.

Схема развёртывания разобрана в [build-and-deploy.md](build-and-deploy.md).
