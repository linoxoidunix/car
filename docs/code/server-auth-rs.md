# 16. `crates/cra-server/src/auth.rs` — три режима аутентификации

**Размер:** 105 строк. **Задача:** установить, кто прислал запрос, — не заводя
собственного хранилища паролей.

## Главное решение: своих паролей нет

Указано в шапке файла:

> Сервис сам НЕ хранит пароли.

Это самая важная мысль в файле. Собственная база учётных записей означала бы:
хеширование паролей, политику сложности, восстановление доступа, блокировку
после неудачных попыток, аудит изменений — и всё это подлежало бы проверке при
аттестации. Причём в организации уже есть домен (ALD Pro / FreeIPA) с
работающим Kerberos-входом.

Поэтому вопрос «кто ты» отдан наружу, а три режима покрывают реальные
развёртывания.

## Режим 1 — `None`

```rust
AuthMode::None => AuthResult::Ok("anonymous".to_string()),
```

Проверки нет. Применяется в доверенном сегменте сети или при разработке.

Даже здесь адрес клиента попадает в журнал: `handlers.rs` пишет `peer` в
каждую запись. Отсутствие аутентификации не означает отсутствия учёта.

## Режим 2 — `Token`

```rust
AuthMode::Token { token } => match req.header("authorization") {
    Some(h) => {
        let presented = h.strip_prefix("Bearer ").unwrap_or(h).trim();
        if constant_time_eq(presented.as_bytes(), token.as_bytes()) {
            AuthResult::Ok("token".to_string())
        } else {
            AuthResult::Denied("invalid token")
        }
    }
    None => AuthResult::Denied("missing authorization header"),
},
```

Общий секрет в заголовке `Authorization: Bearer <token>`. Простейший барьер
для внутреннего инструмента: скрипту нужно передать одну строку.

`strip_prefix("Bearer ").unwrap_or(h)` принимает и полную форму, и голый токен
— удобство для `curl`, не ослабляющее проверку.

Личность здесь буквально `"token"`: кто именно им воспользовался, неизвестно.
Это ограничение режима, и оно честно отражено в журнале.

### Сравнение за постоянное время

```rust
fn constant_time_eq(a: &[u8], b: &[u8]) -> bool {
    if a.len() != b.len() { return false; }
    let mut diff = 0u8;
    for (x, y) in a.iter().zip(b.iter()) {
        diff |= x ^ y;
    }
    diff == 0
}
```

Ключевая деталь: цикл **не прерывается** при первом несовпадении.

Обычное `a == b` останавливается на первом расхождении, поэтому время работы
зависит от длины совпавшего префикса. Атакующий, способный точно измерить это
время, восстанавливает токен посимвольно: перебирает первый символ, находит
чуть более медленный ответ, фиксирует его, переходит ко второму. Вместо
перебора 256^n вариантов получается 256·n — из невозможного становится
осуществимым.

Здесь все байты складываются через XOR в аккумулятор, и время не зависит от
данных. Различие в длине проверяется сразу, поскольку длина токена секретом не
является.

Тест `constant_time_eq_basic` проверяет три случая: совпадение, различие в
середине, различие длины.

## Режим 3 — `Proxy` (основной для развёртывания)

```rust
AuthMode::Proxy { header, trusted } => {
    if !trusted.contains(&peer) {
        return AuthResult::Denied("proxy header from untrusted peer");
    }
    match req.header(&header.to_ascii_lowercase()) {
        Some(user) if !user.trim().is_empty() => AuthResult::Ok(sanitize_principal(user)),
        _ => AuthResult::Denied("missing or empty proxy identity header"),
    }
}
```

Личность утверждает доверенный прокси, стоящий впереди, — тот самый, что
терминирует ГОСТ-TLS. Он выполняет вход в домен (Kerberos/SPNEGO через ALD
Pro) и передаёт имя пользователя в заголовке `X-Remote-User`.

### Проверка адреса — первая, и это принципиально

```rust
if !trusted.contains(&peer) {
    return AuthResult::Denied("proxy header from untrusted peer");
}
```

Заголовок сам по себе не значит ничего: подделать его в `curl` тривиально.
Он приобретает смысл **только** от того, кто его прислал. Поэтому:

1. Служба слушает `127.0.0.1` (умолчание `CRA_ADDR`) — снаружи не достучаться.
2. Заголовок принимается только с адресов из `CRA_TRUSTED_PROXIES`.
3. Прокси **стирает** входящий заголовок и ставит свой:

```nginx
proxy_set_header X-Remote-User "";              # сначала очистить
proxy_set_header X-Remote-User $remote_user;    # затем поставить своё
```

Три меры вместе. Убрать любую — и любой клиент сможет объявить себя кем
угодно. Порядок проверок в коде отражает это: адрес проверяется **до** чтения
заголовка.

### Обеззараживание имени

```rust
fn sanitize_principal(raw: &str) -> String {
    raw.trim()
       .chars()
       .filter(|c| c.is_alphanumeric() || matches!(c, '@' | '.' | '-' | '_' | '\\' | '/'))
       .take(128)
       .collect()
}
```

Имя пользователя попадёт в журнал аудита. Если бы оно содержало `\r\n`,
злоумышленник мог бы **вписать в журнал поддельную строку** — например,
имитировать успешный вход другого пользователя. Это атака внедрения в журнал.

Фильтр оставляет только буквы, цифры и символы, реально встречающиеся в именах:
`@` (user@domain), `\` (DOMAIN\ivanov), `/`, `.`, `-`, `_`.
`.take(128)` ограничивает длину, чтобы гигантское имя не раздуло журнал.

`is_alphanumeric()` в Rust работает по Unicode, поэтому кириллические имена
проходят, а управляющие символы — нет.

Тест `sanitize_strips_control_chars` фиксирует это, включая случай
`"EVIL\r\nSET-COOKIE"` → `"EVILSET-COOKIE"`.

Заметьте: это **вторая** линия обороны. Первая — экранирование в
[`audit.rs`](server-audit-rs.md). Одного слоя хватило бы, но защита в глубину
означает, что ошибка в одном месте не становится уязвимостью.

## Тип результата

```rust
pub enum AuthResult {
    Ok(String),            // имя для журнала
    Denied(&'static str),  // причина для журнала
}
```

Причина отказа — `&'static str`, то есть строковый литерал из программы. Тем
самым в сообщение об ошибке физически не может попасть пользовательский ввод —
ещё одна конструктивная защита от инъекций, на этот раз в теле HTTP-ответа.
