# 6. `crates/cra-core/src/bdd.rs` — двоичные диаграммы решений

**Размер:** 406 строк. **Задача:** хранить булеву функцию в сжатом виде и
уметь по ней (а) точно считать вероятность и (б) находить минимальные наборы.

Это математическое сердце движка.

## Что такое BDD

Возьмём функцию `f = (A И B) ИЛИ V`. Её можно записать таблицей истинности из
2³ = 8 строк. При 30 переменных строк будет миллиард. Нужно что-то компактнее.

**Диаграмма решений** — это дерево вопросов. Спрашиваем про переменные по
очереди, в фиксированном порядке; у каждого узла две ветви:

```
              A?
         0 ╱      ╲ 1
          ╱        ╲
        V?          B?
      0╱ ╲1      0╱   ╲1
      0   1      V?    1
                0╱ ╲1
                 0   1
```

Читается так: «если A ложно, спроси про V; если A истинно, спроси про B» и так
далее. Каждый путь сверху вниз — один набор значений, а лист — результат.

Пока это просто дерево, оно не меньше таблицы. **Сжатие** дают два правила
приведения (отсюда «R» в ROBDD — Reduced Ordered BDD):

1. **Если обе ветви узла ведут в одно и то же — узел не нужен.** Переменная
   ничего не решает, выбрасываем узел, возвращаем ветвь.
2. **Одинаковые узлы существуют в единственном экземпляре.** Если два поддерева
   идентичны, они — один и тот же узел, а не две копии.

После приведения приведённая выше диаграмма выглядит так (подграф `V?`
существует один раз, и на него ссылаются оба места):

```
        A?
     0╱   ╲1
     ╱     B?
    │    0╱ ╲1
    └───►V?   │
        0╱ ╲1 │
         0   1◄┘
```

Два свойства делают ROBDD полезным:

- **каноничность**: при фиксированном порядке переменных у функции ровно одно
  ROBDD. Проверка эквивалентности двух функций — это сравнение двух чисел;
- **разделение подструктур**: одинаковые куски хранятся один раз, поэтому
  реальные схемы надёжности сжимаются очень сильно.

## Структура данных

```rust
struct BddNode { var: u32, lo: u32, hi: u32 }   // lo = ветвь «переменная = 0»

pub struct Bdd {
    nodes: Vec<BddNode>,                            // все узлы в одном массиве
    unique: HashMap<(u32, u32, u32), u32>,          // хеш-консинг
    apply_cache: HashMap<(u8, u32, u32), u32>,      // кеш операций
    not_cache: HashMap<u32, u32>,
}
```

Узлы 0 и 1 всегда зарезервированы под листья `FALSE` и `TRUE`. У них
специальная переменная `TERMINAL_VAR = u32::MAX` — больше любой настоящей,
поэтому в сравнениях `min(var_a, var_b)` листья автоматически оказываются
«ниже всех» и никакой особый случай не нужен.

`var` — это не идентификатор события, а **уровень** в порядке переменных.
Соответствие «уровень → событие или вложенный модуль» хранит `analysis.rs` в
поле `vars` структуры `ModuleData`.

### `mk` — единственный способ создать узел

```rust
fn mk(&mut self, var: u32, lo: u32, hi: u32) -> u32 {
    if lo == hi { return lo; }                              // правило 1
    if let Some(&id) = self.unique.get(&(var, lo, hi)) {    // правило 2
        return id;
    }
    let id = self.nodes.len() as u32;
    self.nodes.push(BddNode { var, lo, hi });
    self.unique.insert((var, lo, hi), id);
    id
}
```

Четыре строки, и это и есть весь ROBDD. Оба правила приведения применяются
принудительно в момент создания, поэтому **неприведённая диаграмма не может
существовать физически**. Приём с таблицей `unique` называется хеш-консингом.

Следствие: если две функции равны, у них один и тот же номер узла. Проверка
эквивалентности — это `a == b`.

## `apply` — операции над функциями

Как построить `f И g`, если f и g уже BDD? Через **разложение Шеннона**:

```
f = (¬x ∧ f|x=0) ∨ (x ∧ f|x=1)
```

Отсюда рекурсия: чтобы применить операцию к двум диаграммам, взять их
верхнюю (наименьшую) переменную, применить операцию к обеим ветвям и собрать
узел:

```rust
let v = na.var.min(nb.var);                      // верхняя переменная из двух
let (a0, a1) = if na.var == v { (na.lo, na.hi) } else { (a, a) };
let (b0, b1) = if nb.var == v { (nb.lo, nb.hi) } else { (b, b) };
let lo = self.apply(op, a0, b0);
let hi = self.apply(op, a1, b1);
let r = self.mk(v, lo, hi);
```

Строчка `else { (a, a) }` — существенная: если у `a` верхняя переменная другая,
значит `a` от `v` не зависит, и обе ветви равны самому `a`.

### Что делает это быстрым

**Терминальные случаи** обрываются немедленно:

```rust
Op::And => {
    if a == FALSE || b == FALSE { return FALSE; }   // «ложь И что угодно»
    if a == TRUE { return b; }
    if b == TRUE || a == b { return a; }            // «a И a = a»
}
```

Проверка `a == b` работает только потому, что диаграммы канонические.

**Кеш операций** — то, что превращает экспоненту в полином:

```rust
let key = (op as u8, a.min(b), a.max(b));   // И/ИЛИ/XOR коммутативны
if let Some(&r) = self.apply_cache.get(&key) { return r; }
```

Нормализация ключа через `min`/`max` использует коммутативность: `f И g` и
`g И f` попадают в одну ячейку кеша, вдвое повышая попадание. Благодаря кешу
каждая пара подграфов обрабатывается ровно один раз, и `apply` стоит
O(|f| × |g|) вместо экспоненты.

### `not`

Отрицание рекурсивно инвертирует обе ветви. Кеш пополняется в обе стороны:

```rust
self.not_cache.insert(a, r);
self.not_cache.insert(r, a);      // ¬¬f = f — известно бесплатно
```

Тест `not_is_involution` проверяет, что двойное отрицание даёт **тот же самый
номер узла**, а не просто эквивалентную функцию. Это утверждение о
каноничности.

### `atleast` — «k из n»

Мажоритарные схемы («работают минимум 2 датчика из 3») встречаются в
надёжности постоянно. Наивное построение перебрало бы все C(n,k) сочетаний —
для «10 из 20» это 184 756 элементов И.

Вместо этого — рекурсия с мемоизацией:

```
f(i, k) = (x_i И f(i+1, k−1))  ИЛИ  f(i+1, k)
             ^ берём вход i          ^ пропускаем вход i
```

с базой `k == 0 → TRUE` (набрали достаточно) и `осталось < k → FALSE` (уже не
наберём). Мемоизация по `(i, k)` даёт O(n·k) подзадач вместо C(n,k).

**Разбор — 2 из 3, q = 0,1 у каждого:**

```
P = 3q²(1−q) + q³ = 3 × 0,01 × 0,9 + 0,001 = 0,027 + 0,001 = 0,028
```

Тест `two_of_three` проверяет ровно это число и заодно то, что минимальных
сечений три (`{1,2}`, `{1,3}`, `{2,3}`), каждое с вероятностью 0,01.

## `prob` — точная вероятность

Здесь окупается вся конструкция.

```rust
fn prob_rec(&self, u, p, memo) -> f64 {
    if u == FALSE { return 0.0; }
    if u == TRUE  { return 1.0; }
    if let Some(&r) = memo.get(&u) { return r; }
    let n = self.nodes[u as usize];
    let pv = p[n.var as usize];
    let r = pv * self.prob_rec(n.hi, p, memo)
          + (1.0 - pv) * self.prob_rec(n.lo, p, memo);
    memo.insert(u, r);
    r
}
```

Формула полной вероятности в каждом узле:

```
P(узел) = P(переменная) · P(ветвь hi) + (1 − P(переменная)) · P(ветвь lo)
```

**Почему это точно, а не приближённо.** Ветви `hi` и `lo` соответствуют
*непересекающимся* событиям (переменная либо истинна, либо ложна). Значит,
вероятности просто складываются — без формулы включений-исключений, без
пересечений, без поправок. Структура BDD **автоматически** производит
разбиение пространства на непересекающиеся события, из-за чего и получается
точный ответ даже при общих переменных.

Сравните с наивным «сложить вероятности сечений» — это лишь приближение редких
событий, всегда завышающее ответ.

Мемоизация означает, что каждый узел вычисляется один раз: стоимость — один
проход по сжатому графу, O(|BDD|).

### Разбор на нашей станции

Переменные: уровень 0 = A, 1 = B, 2 = V, вероятности `p = [0,1, 0,1, 0,05]`.
Диаграмма `(A И B) ИЛИ V`:

```
P = 0,1 · P(B И … ИЛИ V) + 0,9 · P(V)
  = 0,1 · [0,1 · 1 + 0,9 · 0,05] + 0,9 · 0,05
  = 0,1 · 0,145 + 0,045
  = 0,0145 + 0,045
  = 0,0595                              ✔ совпало с ручным счётом
```

Тест `and_or_prob` проверяет базовые случаи: `P(x И y) = 0,02` и
`P(x ИЛИ y) = 0,28` при p = [0,1, 0,2]. Обратите внимание на второй: наивное
сложение дало бы 0,3, точный ответ 0,1 + 0,2 − 0,02 = 0,28.

## `minsol` — минимальные наборы (алгоритм Рози)

Второй большой алгоритм файла. Он находит **минимальные наборы переменных,
истинность которых делает функцию истинной**, то есть минимальные сечения.

### Рекурсия

Идём по диаграмме сверху вниз. Для узла с переменной `x`:

- решения ветви `lo` — это решения, где `x` **не нужна**; берём как есть;
- решения ветви `hi`, к каждому добавлен `x` — решения, где `x` требуется.

```rust
let s0 = minsol_rec(n.lo, …);   // решения без переменной этого узла
let s1 = minsol_rec(n.hi, …);   // решения, требующие её
let mut res = (*s0).clone();
for (c, cp) in s1.iter() {
    if s0.iter().any(|(z, _)| is_subset(z, c)) { continue; }   // ПОГЛОЩЕНИЕ
    res.push(({x} ∪ c, p_x · cp));
}
```

### Поглощение — та самая строчка, что даёт минимальность

```rust
if s0.iter().any(|(z, _)| is_subset(z, c)) { continue; }
```

Читается: «если какое-то решение `z` из ветви `lo` целиком содержится в
кандидате `c`, то набор `{x} ∪ c` **не минимален** — ведь `z` работает и без
`x`, и он меньше. Выбрасываем».

Именно это отсекает `{A, B, V}` в нашем примере: ветвь `lo` содержит `{V}`,
`{V} ⊆ {V}` — кандидат `{A,B,V}` поглощён.

Проверка на подмножество написана для **отсортированных** наборов и работает
за линейное время слиянием:

```rust
fn is_subset(a: &[u32], b: &[u32]) -> bool {
    let mut j = 0usize;
    for &x in a {
        while j < b.len() && b[j] < x { j += 1; }
        if j >= b.len() || b[j] != x { return false; }
        j += 1;
    }
    true
}
```

Наборы отсортированы автоматически: BDD обходится в порядке уровней, поэтому
переменные добавляются по возрастанию. Приятное следствие структуры, не
требующее сортировки.

Тест `minsol_subsumes` фиксирует это на `f = a ИЛИ (a И b)`: единственное
минимальное решение — `{a}`.

### Мемоизация через `Rc`

```rust
memo: HashMap<u32, Rc<Vec<(Vec<u32>, f64)>>>
```

`Rc` — счётчик ссылок: список решений подграфа вычисляется один раз, и все
места, которые на него ссылаются, разделяют одну копию, а не копируют вектор.
На больших диаграммах со множеством общих подграфов это экономит огромную
память.

### Обрезка — три предохранителя

Число минимальных сечений может расти экспоненциально даже когда BDD компактен.
Поэтому три ограничителя:

| Параметр | Действие |
|---|---|
| `max_order` | выбрасывает наборы длиннее N элементов |
| `cutoff` | выбрасывает наборы с вероятностью ниже порога |
| `max_sets` | ограничивает число хранимых наборов |

Ключевая деталь — **что именно оставляют при переполнении**:

```rust
if res.len() > max_sets {
    res.select_nth_unstable_by(max_sets - 1, |a, b| {
        b.1.partial_cmp(&a.1).unwrap_or(std::cmp::Ordering::Equal)
    });
    res.truncate(max_sets);
    *truncated = true;
}
```

Оставляют **самые вероятные**, а не первые попавшиеся. Это правильно
инженерно: смысл списка сечений в том, чтобы показать, что вероятнее всего
уронит систему; отбрасывать надо маловероятную мелочь.

`select_nth_unstable_by` — быстрый выбор (quickselect) за O(n), а не полная
сортировка за O(n log n): нам не нужен упорядоченный список, нужны лишь N
лучших.

Флаг `truncated` идёт наверх и превращается в предупреждение в JSON-ответе,
чтобы пользователь знал, что список неполон.

Тест `minsol_truncation_keeps_most_probable` проверяет именно приоритет: при
`f = a ИЛИ b ИЛИ c` с вероятностями `[0,001, 0,5, 0,2]` и лимитом в 2 набора
остаются `b` и `c`, а редкое `a` отбрасывается.

**Важно:** обрезается только *список наборов*. Вероятность вершины считается
через `prob` и не усекается никогда.

## Порядок переменных — молчаливое допущение

Размер BDD критически зависит от порядка переменных: у одной функции может
быть 20 узлов при хорошем порядке и 2^n при плохом. Поиск оптимального порядка
NP-труден.

Этот файл порядок **не выбирает** — он получает уровни готовыми. Выбор делает
`analysis.rs`: порядок первого вхождения при обходе в глубину. Эвристика
простая, но проверенная временем: переменные, встречающиеся в схеме рядом,
получают соседние уровни, и подграфы хорошо разделяются. См.
[core-analysis-rs.md](core-analysis-rs.md).
