# 7. `crates/cra-core/src/analysis.rs` — главный конвейер

**Размер:** 602 строки. **Задача:** связать декомпозицию, BDD и распределения в
один расчёт и собрать ответ.

Это дирижёр. Здесь живёт `analyze_request` — единственная функция, которую
вызывают оба фронтенда.

## Четыре шага

```
1) разбить схему на модули (независимые части)
2) на каждый модуль построить свой BDD
3) снизу вверх собрать точную вероятность вершины
4) минимальные наборы: minsol на каждый модуль, затем свёртка
```

## Структуры данных

```rust
enum LocalVar {
    Event(EventId),    // переменная BDD = базовое событие
    Module(usize),     // переменная BDD = вложенный модуль (псевдособытие)
}

struct ModuleData {
    bdd: Bdd,
    bdd_root: u32,
    vars: Vec<LocalVar>,   // уровень BDD → что он означает
    root: NodeId,          // узел формулы, чья функция этот модуль (для имени)
}

struct Compiled {
    mods: Vec<ModuleData>,  // дети идут раньше родителей
    top: usize,
}
```

`vars` — это словарь перевода. BDD знает только «уровень 0», «уровень 1»; чтобы
подставить вероятность, нужно понять, что скрыто за уровнем: событие (взять
`p_event[e]`) или вложенный модуль (взять его уже посчитанную вероятность).

Порядок в `mods` таков, что дети всегда идут раньше родителей — это следствие
рекурсии в `process_module`, и на нём держится один-единственный проход в
`module_probs`.

## Шаг 1–2: `compile_modules` и `process_module`

```rust
fn compile_modules(f: &Formula) -> Compiled {
    let modset = find_modules(f);              // → module.rs
    let top = process_module(f, &modset, f.root, &mut done, &mut mods);
    Compiled { mods, top }
}
```

`process_module` для одного модуля делает две вещи.

### а) Собрать локальные переменные обходом в глубину

```rust
let mut stack: Vec<NodeId> = vec![root];
while let Some(v) = stack.pop() {
    if v != root && modset.contains(&v) {
        let mi = process_module(f, modset, v, done, mods);   // рекурсия!
        node_level.insert(v, vars.len() as u32);
        vars.push(LocalVar::Module(mi));
        continue;                             // НЕ идём внутрь вложенного модуля
    }
    match &f.nodes[v] {
        Node::Var(e) => {
            node_level.insert(v, vars.len() as u32);
            vars.push(LocalVar::Event(*e));
        }
        _ => { /* положить детей на стек */ }
    }
}
```

Две решающие строки:

1. `if v != root && modset.contains(&v)` — наткнувшись на вложенный модуль,
   обход **останавливается**. Модуль обрабатывается отдельной рекурсией и
   становится одной переменной. Ровно этим достигается декомпозиция.
2. Порядок, в котором переменные добавляются в `vars`, **и есть порядок
   переменных BDD** — эвристика «первое вхождение при DFS».

Мемоизация `done: HashMap<NodeId, usize>` обеспечивает, что модуль с двумя
родителями (случай `shared_gate_with_private_subtree_is_module` из
[`module.rs`](core-module-rs.md)) компилируется один раз.

Дети кладутся на стек в обратном порядке:

```rust
for i in (0..f.child_count(v)).rev() { … }
```

Стек LIFO, поэтому обратный порядок укладки даёт прямой порядок обхода — левые
входы получают младшие уровни.

### б) Перевести формулу в BDD

```rust
fn translate(f, v, node_level, bdd, memo) -> u32 {
    if let Some(&lvl) = node_level.get(&v) {
        bdd.var(lvl)                    // это переменная (событие или модуль)
    } else {
        match &f.nodes[v] {
            Node::And(cs) => { /* сложить через bdd.and */ }
            Node::Or(cs)  => { /* сложить через bdd.or  */ }
            Node::Not(c)  => bdd.not(translate(c)),
            Node::AtLeast { k, args } => bdd.atleast(*k, &xs),
            …
        }
    }
}
```

Прямая рекурсия по структуре формулы. Мемоизация `memo` гарантирует, что общий
подграф формулы переводится один раз.

Обратите внимание на аккумуляторы: `And` начинается с `TRUE`, `Or` — с
`FALSE`, `Xor` — с `FALSE`. Это нейтральные элементы операций, поэтому элемент
с одним входом корректно вырождается в сам вход.

## Шаг 3: `module_probs` — сборка снизу вверх

```rust
fn module_probs(c: &Compiled, p_event: &[f64]) -> Vec<f64> {
    let mut out = vec![0.0f64; c.mods.len()];
    for i in 0..c.mods.len() {
        let vp: Vec<f64> = c.mods[i].vars.iter().map(|v| match v {
            LocalVar::Event(e)  => p_event[*e],
            LocalVar::Module(j) => out[*j],      // уже посчитан
        }).collect();
        out[i] = c.mods[i].bdd.prob(c.mods[i].bdd_root, &vp);
    }
    out
}
```

Один простой цикл — никакой рекурсии, никакой сортировки. Работает потому, что
дети лежат в `mods` раньше родителей, значит `out[*j]` к моменту обращения уже
заполнен.

Результат `out[c.top]` — вероятность вершины. **Точная.**

### Разбор на насосной станции

Модули: `M0 = И(A,B)` и `M1 = ИЛИ(M0, V)` (вершина).

```
шаг i=0: vp = [q_A, q_B] = [0,1, 0,1]     → out[0] = 0,01
шаг i=1: vp = [out[0], q_V] = [0,01, 0,05] → out[1] = 1 − 0,99·0,95 = 0,0595
```

Ответ `out[top] = 0,0595`. ✔

## Шаг 4: минимальные наборы и свёртка

Здесь самое хитрое место файла.

### Задача

`minsol` работает **внутри одного модуля** и возвращает наборы из локальных
переменных — а среди них есть псевдопеременные-модули. Набор вида
`{M0, …}` пользователю не нужен, ему нужны имена настоящих элементов. Значит,
вместо переменной-модуля надо подставить **его собственные** минимальные
наборы, и сделать это для всех сочетаний — то есть выполнить декартово
произведение (свёртку).

### `expand` — рекурсивная свёртка

```rust
for (set, _) in &local {                       // каждый локальный набор
    let mut acc = vec![(Vec::new(), 1.0)];     // «частично собранные» наборы
    for &lvl in set {                          // каждая переменная набора
        match md.vars[lvl as usize] {
            LocalVar::Event(e) => {
                // дописать событие ко всем частичным наборам
            }
            LocalVar::Module(j) => {
                let sub = expand(ctx, j);      // рекурсия
                // ДЕКАРТОВО ПРОИЗВЕДЕНИЕ acc × sub
            }
        }
    }
    out.extend(acc);
}
```

**Разбор.** Пусть локальный набор модуля — `{M0, M1}`, где

```
у M0 минимальные наборы: {a}, {b}
у M1 минимальные наборы: {c}, {d}
```

Свёртка даёт `2 × 2 = 4` глобальных набора: `{a,c}, {a,d}, {b,c}, {b,d}`, с
вероятностями, равными произведениям.

Отсюда видно, почему обрезка обязательна: при цепочке из десяти модулей по
десять наборов в каждом произведение даёт 10^10 наборов. Пределы проверяются
**внутри** циклов свёртки, до того как набор построен:

```rust
if ev.len() + sev.len() <= ctx.max_order && npr >= ctx.cutoff { … }
else { ctx.truncated = true; }
```

### Почему свёртка сохраняет минимальность

Комментарий в коде: «Модули независимы и не делят события, so minimal sets stay
minimal». Это существенно. Поскольку модули не имеют общих базовых событий,
набор, собранный из минимальных наборов разных модулей, не может содержать
внутри себя другой такой набор. Дополнительная проверка на поглощение после
свёртки не нужна — и это огромная экономия, ведь попарная проверка поглощения
на списке в 20 000 наборов стоила бы O(n²).

Мемоизация — вектор `ctx.memo: Vec<Option<Rc<…>>>`, индексируемый номером
модуля: каждый модуль разворачивается один раз, даже если на него ссылаются из
нескольких мест.

### `minimal_sets` — обёртка

```rust
for (ev, _) in result.iter_mut() { ev.sort_unstable(); }
result.sort_by(|a, b| b.1.partial_cmp(&a.1).unwrap_or(Ordering::Equal));
```

Сортировка событий внутри набора даёт детерминированный вывод; сортировка
наборов по убыванию вероятности ставит важное наверх — первое, что видит
пользователь, это самое вероятное сечение.

`partial_cmp(...).unwrap_or(Equal)` — защита от NaN: у `f64` нет полного
порядка, а сортировка с непоследовательным компаратором в Rust может вызвать
панику. Такая запись делает NaN «равным» и не роняет процесс.

## Развилка «сечения или пути» — `analyze_system`

Самое тонкое рассуждение в файле:

```rust
// Прямой minsol = наборы, которые делают вершину ИСТИННОЙ.
// Двойственный minsol = наборы, ложность которых делает вершину ЛОЖНОЙ.
// Дерево (вершина = отказ):  прямой → сечения,  двойственный → пути.
// СФЦ    (вершина = критерий): прямой → пути,   двойственный → сечения.
```

Разберём по шагам:

- **Дерево отказов.** `Var` истинно = «элемент отказал», вершина = «система
  отказала». Минимальные решения = минимальные наборы отказов, валящие
  систему = **сечения**. Двойственная функция даёт **пути**.
- **СФЦ.** `Var` истинно = «элемент работает», вершина = «критерий выполнен».
  Минимальные решения = минимальные наборы работающих элементов, обеспечивающих
  работу = **пути**. Двойственная даёт **сечения**.

Код выражает это без единого дублирования:

```rust
let want_primary = match sys.kind {
    ModelKind::FaultTree => opts.cut_sets,
    ModelKind::Sfc       => opts.path_sets,
};
let primary = if want_primary { minimal_sets(&sys.formula, p0, opts) } … ;
let dual    = if want_dual    { minimal_sets(&sys.formula.dual(), &dual_p, opts) } … ;
let (cut_sets, path_sets) = match sys.kind {
    ModelKind::FaultTree => (primary, dual),
    ModelKind::Sfc       => (dual, primary),
};
```

Вероятности для двойственной задачи тоже переворачиваются:

```rust
let dual_p: Vec<f64> = p0.iter().map(|p| 1.0 - p).collect();
```

Это следует прямо из определения `f^D(x) = ¬f(¬x)`: раз переменные
инвертируются, инвертируются и их вероятности.

### Проверка на станции

```
Сечения (прямой, p = [0,1, 0,1, 0,05]):
   {V}     P = 0,05
   {A,B}   P = 0,01

Пути (двойственная, p = [0,9, 0,9, 0,95]):
   {A,V}   P = 0,9 × 0,95 = 0,855
   {B,V}   P = 0,9 × 0,95 = 0,855
```

Совпадает с ручным счётом из [вводной главы](00-concepts.md). ✔

## Несколько моментов времени

```rust
let times: Vec<f64> = match &req.times {
    Some(ts) if !ts.is_empty() => ts.clone(),
    _ => vec![req.mission_time.unwrap_or(0.0)],
};
```

`times` приоритетнее `mission_time`; если нет ни того, ни другого — берётся 0.
Каждое время проверяется на конечность и неотрицательность.

Вероятность вершины считается для **каждого** времени, а вот структура
(модули, BDD) строится **один раз** — она от времени не зависит, меняются
только числа на входе `module_probs`. Поэтому кривая q(t) из 60 точек стоит
почти столько же, сколько одна точка. Именно этим пользуется график в
марковском окне веб-интерфейса.

Минимальные наборы считаются только для **первого** времени (`p_by_time[0]`) —
их состав от времени не зависит, меняются лишь вероятности. Это отражено в
описании поля: «Probability of the set at the first evaluation time».

## Отчёт — `sets_report`

```rust
let rare_event: f64 = sets.iter().map(|(_, p)| p).sum();
let ep = 1.0 - sets.iter().map(|(_, p)| 1.0 - p).product::<f64>();
```

Две классические оценки, которые дают почувствовать качество усечения:

- **Приближение редких событий** — просто сумма вероятностей наборов. Всегда
  завышает (не учитывает пересечения), просто и привычно.
- **Граница Эзари–Прошана** `1 − Π(1 − P_i)` — верхняя граница для монотонных
  систем, всегда точнее суммы.

Для станции: сумма = 0,05 + 0,01 = 0,06; Эзари–Прошан = 1 − 0,95 × 0,99 =
0,0595. Второе значение совпало с точным, потому что наборы здесь
непересекающиеся. Сравнение этих чисел с `top_probability` показывает, много ли
потеряно при усечении.

## ROBDD наружу — `bdd_report`

С флагом `options.bdd` ответ несёт сами диаграммы модулей — ровно те, по
которым посчитана `top_probability`. Веб-интерфейс рисует их в результатах.

```rust
let bdd = opts.bdd.then(|| bdd_report(&compiled, sys, p0, opts.bdd_max_nodes));
```

Для каждого модуля:

- **узлы** — `Bdd::export`: только достижимые из корня, сверху вниз, с id от 2
  (0 и 1 — листья FALSE и TRUE);
- **переменные по уровням** — событие (по имени) или вложенный модуль (по
  индексу в списке модулей), у каждой вероятность быть истинной;
- **вероятность каждого узла** — то же разложение Шеннона, что в `Bdd::prob`:
  `P(u) = p·P(hi) + (1 − p)·P(lo)`. Дети стоят в списке после родителей, так что
  хватает одного прохода с конца. Вероятность корня равна вероятности модуля;
- **имя** — элемент дерева или узел СФЦ, чья функция этот модуль
  (`System::labels`). У служебных узлов (скажем, группа дизъюнктивных дуг
  внутри вершины СФЦ) имени нет.

Все вероятности — для первого момента времени, как и у наборов.

**Предел размера.** Диаграмма бывает огромной, а рисовать и пересылать её
незачем целиком. `bdd_max_nodes` (по умолчанию 2000) ограничивает сумму узлов
по модулям. Бюджет раздаётся от вершины вниз: модули построены детьми вперёд,
поэтому цикл идёт с конца — вершина важнее вложенных модулей. Модуль, который
не влез, выдаётся без узлов, но с размером (`size`), а в `warnings` появляется
предупреждение.

Без флага `bdd_report` не вызывается вовсе, и поле `bdd` в JSON отсутствует:
прежние ответы не изменились ни на байт.

## Меры значимости — `importance_report`

С флагом `options.importance` ответ несёт для каждого базового события четыре
меры значимости. Все они выводятся из одной — **меры Бирнбаума** `I_B = ∂Q/∂q`
(насколько вероятность отказа системы чувствительна к вероятности отказа
элемента).

### Бирнбаум для всех событий сразу — `birnbaum`

В каждом модуле `Bdd::derivatives` даёт производные его вероятности по всем его
переменным за два прохода (см. [core-bdd-rs.md](core-bdd-rs.md)). Вложенный
модуль — переменная родителя, поэтому производные сцепляются по цепному
правилу:

```
∂P_top/∂p_e = ∂P_top/∂P_m · ∂P_m/∂p_e      (m — модуль, где e стоит переменной)
```

```rust
d_mod[c.top] = 1.0;
for i in (0..c.mods.len()).rev() {            // от вершины: родитель раньше детей
    let d = m.bdd.derivatives(m.bdd_root, &var_probs(m, p_event, &mod_p));
    for (v, dv) in m.vars.iter().zip(d) {
        match v {
            LocalVar::Event(e) => out[*e] += d_mod[i] * dv,
            LocalVar::Module(j) => d_mod[*j] += d_mod[i] * dv,
        }
    }
}
```

Сумма здесь складывает по одному слагаемому: модуль входит переменной ровно в
одного родителя (если бы его разделяли два модуля, ни один из них не был бы
модулем), а событие — ровно в один модуль. Итого вся работа — два линейных
прохода по каждой BDD, столько же, сколько стоит сама вероятность.

### Остальные меры — из Бирнбаума

Вероятность полилинейна, поэтому по `I_B` восстанавливается вероятность отказа
системы при «элемент отказал наверняка» и при «элемент абсолютно надёжен»:

```
Q(q = 1) = Q + (1 − q)·I_B          Q(q = 0) = Q − q·I_B
```

| Мера | Формула | Смысл |
|---|---|---|
| Бирнбаум | `∂Q/∂q = Q(q=1) − Q(q=0)` | чувствительность: сколько даёт улучшение элемента |
| Критичность (Фусселл–Везели) | `q·I_B / Q = (Q − Q(q=0)) / Q` | доля риска, связанная с элементом |
| RAW | `Q(q=1) / Q` | во сколько раз вырастет риск, если элемент отказал |
| RRW | `Q / Q(q=0)` | во сколько раз упадёт риск, если элемент безотказен |

Фусселл–Везели здесь — в форме «снижения риска», принятой в
вероятностном анализе безопасности (FV = 1 − 1/RRW); в этой форме он совпадает
с критичностью. Классический вариант через сечения (вероятность объединения
сечений с элементом, делённая на Q) для монотонной схемы не меньше этого.

Меры **в терминах отказа в обеих нотациях**: в СФЦ вершина — критерий (успех),
переменная — «элемент работает», но `∂P/∂p = ∂Q/∂q` (оба знака меняются), так
что меняются только `Q = 1 − P` и `q = 1 − p`. Таблица значимости читается
одинаково для дерева и для СФЦ.

Края: при `Q = 0` критичность, RAW и RRW не определены (`null`). Если элемент
в одиночку держит систему (`Q(q=0) = 0`), RRW бесконечен — тоже `null`; ноль,
испорченный округлением, отсекается порогом `Q·10⁻¹²`. Для немонотонной схемы
`I_B` бывает отрицательным: улучшение элемента ухудшает систему. События, не
входящие в схему, получают нули (RAW = RRW = 1). Список отсортирован по
критичности, при равенстве — по Бирнбауму. Значения — для первого момента
времени.

## Предупреждения

```rust
if noncoherent && (opts.cut_sets || opts.path_sets) {
    warnings.push("model is non-coherent (contains NOT/XOR): minimal sets are \
                   computed from positive literals only and may be approximate");
}
```

Честное признание границ применимости. Для немонотонной схемы (есть НЕ или
XOR) понятие «минимального сечения» само по себе становится неоднозначным:
строго говоря, нужны «главные импликанты» с отрицательными литералами. Движок
считает **вероятность точно** (BDD обрабатывает отрицания без всяких проблем),
но список наборов строит только по положительным литералам и честно об этом
сообщает.

Отдельные предупреждения выдаются при усечении списков.

## `Stats` — что вернулось в статистике

```rust
Stats {
    events,         // сколько базовых событий
    formula_nodes,  // размер логического графа
    modules,        // сколько модулей нашлось  ← показатель качества декомпозиции
    bdd_nodes,      // суммарный размер всех BDD ← показатель сложности
    noncoherent,
}
```

`modules` и `bdd_nodes` — диагностика. `bdd_nodes` считает все узлы,
созданные при построении (с промежуточными и листьями), поэтому он больше
суммы `size` в отчёте `bdd`, где только сами функции. Много модулей и мало узлов BDD означает,
что схема разложилась удачно и посчиталась быстро. Один модуль и сотни тысяч
узлов BDD означают сильно связанную схему, где помочь нечем.
