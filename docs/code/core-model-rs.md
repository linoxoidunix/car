# 2. `crates/cra-core/src/model.rs` — внутренний логический граф

**Размер:** 146 строк. **Задача:** определить единственную структуру данных, к
которой сводятся обе входные нотации (дерево отказов и СФЦ), чтобы весь
остальной движок имел дело только с одной формой.

## Какую задачу решает

На вход движка приходят две совершенно по-разному выглядящие вещи:

- **дерево отказов**: «вершина = ИЛИ этих элементов, каждый элемент = И этих
  событий»;
- **СФЦ**: «у узла n3 конъюнктивная дуга от n1 и дизъюнктивная инверсная дуга
  от n2; критерий — выход n3».

Писать построитель BDD, декомпозицию и расчёт вероятности дважды — по разу на
нотацию — означало бы удвоить код и удвоить ошибки. Поэтому `io.rs` переводит
обе нотации в `Formula`, а всё, что дальше (`module.rs`, `bdd.rs`,
`analysis.rs`), видит только `Formula`.

## Структуры данных

### `Node` — одна операция

```rust
pub enum Node {
    True,
    False,
    Var(EventId),                       // базовое событие
    Not(NodeId),
    And(Vec<NodeId>),
    Or(Vec<NodeId>),
    Xor(Vec<NodeId>),
    AtLeast { k: usize, args: Vec<NodeId> },   // «k из n»
}
```

`enum` в Rust означает «ровно одна из этих форм». Узел — это *либо*
переменная, *либо* И, *либо* ИЛИ, никогда не два сразу, и компилятор
заставляет каждый кусок кода, который смотрит на узел, обработать все случаи.

### `Formula` — все узлы в одном массиве

```rust
pub struct Formula {
    pub nodes: Vec<Node>,   // плоский массив
    pub root: NodeId,       // индекс вершины
}
pub type NodeId = usize;    // «указатель» = индекс в массиве
```

Никаких указателей и боксов. Ребёнок задаётся своим **индексом** в `nodes`.
Это осознанный выбор:

- вся формула — одно непрерывное выделение памяти: быстро и хорошо ложится в
  кеш процессора;
- алгоритм может завести побочные таблицы вида `vec![0usize; nodes.len()]` и
  индексировать их прямо по `NodeId` (на этом построены и `module.rs`, и
  `analysis.rs`);
- нет подсчёта ссылок и головоломок с временами жизни.

### Разобранный пример — наша насосная станция

`(A И B) ИЛИ V`, где A, B, V — базовые события 0, 1, 2:

```rust
let mut f = Formula::default();
let a  = f.add(Node::Var(0));            // индекс 0
let b  = f.add(Node::Var(1));            // индекс 1
let v  = f.add(Node::Var(2));            // индекс 2
let g1 = f.add(Node::And(vec![a, b]));   // индекс 3
let top= f.add(Node::Or(vec![g1, v]));   // индекс 4
f.root = top;
```

Массив теперь такой:

```
индекс: 0        1        2        3            4
узел:   Var(0)   Var(1)   Var(2)   And([0,1])   Or([3,2])
                                                     ^ корень
```

`f.add(node)` дописывает узел в конец и возвращает новый индекс — весь метод в
двух строчках.

### Почему это ДАГ, а не дерево

Ничто не мешает двум родителям указать один и тот же индекс ребёнка. Если
событие `V` питает три элемента, все три хранят число `2`. Значит, структура —
это **направленный ациклический граф**, и одному базовому событию соответствует
ровно один узел `Var` (это гарантирует `io.rs`). Циклы отвергаются на этапе
сборки.

Именно это разделение общих узлов и делает анализ трудным — общие события
разрушают независимость — и именно его обнаруживает `module.rs`.

## Вспомогательные методы

| Метод | Назначение |
|---|---|
| `add(node) -> NodeId` | добавить, вернуть индекс |
| `child_count(id)`, `child_at(id, i)` | единообразно обходить детей, каким бы ни был тип узла. Все обходы в движке написаны через эти два метода, поэтому добавление нового типа элемента затрагивает один файл. |
| `is_gate(id)` | истина для всего, что не лист (`True`/`False`/`Var`), то есть для кандидата в модули |
| `has_negation()` | истина, если есть хоть один `Not` или `Xor` → схема **немонотонная**, минимальные наборы становятся приближёнными, выдаётся предупреждение |

## Двойственная функция — как пути получаются бесплатно

Это самая интересная функция в файле.

```rust
pub fn dual(&self) -> Formula      // f^D(x) = ¬f(¬x)
```

### Идея

Вычисление минимальных *сечений* — решённая задача (`minsol` в `bdd.rs`): она
находит минимальные группы переменных, делающие функцию **истинной**.

Минимальные *пути* — это минимальные группы, ложность которых делает функцию
ложной. Другой вопрос, требующий другого алгоритма.

Если только не воспользоваться двойственностью. Классический результат:

> **Минимальные решения двойственной функции — это минимальные пути исходной
> функции** (и наоборот).

Поэтому вместо второго алгоритма движок строит `f.dual()` и запускает на нём
*тот же самый* `minsol`. Один алгоритм — оба результата.

### Как строится двойственная формула

Законы Де Моргана говорят `¬(x И y) = ¬x ИЛИ ¬y`. Применение `¬f(¬x)` сводится
к замене операций местами, переменные при этом не трогаются:

| исходная | двойственная |
|---|---|
| `And(v)` | `Or(v)` |
| `Or(v)` | `And(v)` |
| `True` | `False` |
| `Var(e)` | `Var(e)` — без изменений |
| `Not(c)` | `Not(c)` — без изменений |
| `AtLeast{k, n аргументов}` | `AtLeast{n − k + 1, те же аргументы}` |

Правило для `AtLeast` стоит проверить руками: двойственная к «не менее 2 из 3»
есть «не менее 3 − 2 + 1 = 2 из 3» — мажоритарный элемент 2-из-3 самодвойствен,
и это верно. Двойственная к «не менее 1 из 3» (то есть к ИЛИ) есть «не менее 3
из 3» (то есть И) — тоже верно.

`Xor` требует особого случая, потому что `xor(¬x) = xor(x)` при нечётном числе
входов, но `= ¬xor(x)` при чётном. Для чётного случая код дописывает
дополнительный узел и оборачивает его в `Not`:

```rust
Node::Xor(v) => {
    if v.len() % 2 == 1 { Node::Xor(v.clone()) }        // двойственная == сама себе
    else {                                              // двойственная == not(xor)
        let j = n + extra.len();
        extra.push(Node::Xor(v.clone()));
        Node::Not(j)
    }
}
```

Вектор `extra` дописывается после основного массива — поэтому новые индексы
считаются как `n + extra.len()`, где `n` — исходная длина.

### Проверка на нашем примере

Исходная: `(A ∧ B) ∨ V`. Двойственная: `(A ∨ B) ∧ V`.
Минимальные решения двойственной: `{A, V}` и `{B, V}` — ровно те минимальные
пути, которые мы посчитали руками во [вводной главе](00-concepts.md). ✔

## `ModelKind` — единственный флаг, помнящий нотацию

```rust
pub enum ModelKind {
    FaultTree,   // Var(e) ИСТИНА ⇔ элемент ОТКАЗАЛ.  P(Var) = q(t)
    Sfc,         // Var(e) ИСТИНА ⇔ элемент РАБОТАЕТ. P(Var) = 1 − q(t)
}
```

Этот единственный флаг переворачивает смысл всего дальнейшего, и применяется он
ровно в одном месте:

```rust
pub fn var_prob(&self, e: EventId, t: f64) -> f64 {
    let q = self.events[e].model.unavailability(t);
    match self.kind {
        ModelKind::FaultTree => q,
        ModelKind::Sfc       => 1.0 - q,
    }
}
```

Всё остальное в движке от нотации не зависит. Единственное другое место, где
флаг важен, — `analysis.rs`, где решается, чем являются *прямые* минимальные
наборы: сечениями (дерево отказов) или путями (СФЦ), см.
[core-analysis-rs.md](core-analysis-rs.md).

## `System` — собранный объект, готовый к расчёту

```rust
pub struct System {
    pub kind: ModelKind,
    pub events: Vec<BasicEvent>,     // имя + закон отказа, индексируется EventId
    pub formula: Formula,
    pub labels: HashMap<NodeId, String>,  // узел формулы → имя элемента / узла СФЦ
}
```

Это результат работы `io::compile()` и вход для `analyze_system()`.
`labels` расчёту не нужны: по ним выдача ROBDD называет модули по элементам
схемы (см. [core-io-rs.md](core-io-rs.md), `name_nodes`).
`BasicEvent` хранит понятное человеку имя (используется при печати сечений) и
`ReliabilityModel` из [`dist.rs`](core-dist-rs.md).
