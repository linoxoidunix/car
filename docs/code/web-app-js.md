## Модель данных

Три переменные хранят всё состояние:

```js
let graph = { kind: "fault_tree", nodes: [], edges: [] };
let selNodes = new Set();   // id выбранных узлов (можно несколько)
let selEdge = null;        // выбранная связь {parent, child}
const view = { tx: 40, ty: 40, s: 1 };   // сдвиг и масштаб холста
```

Формат узла и связи:

```js
// graph.nodes: { id, x, y, role, op?, k?, dist?, top? }
//   role = "event" | "gate"  (дерево)  |  "sfc"  (узел СФЦ / фиктивный)
//   dist = объект распределения, готовый к отправке (null = фиктивный узел)
// graph.edges: { parent, child, inverse?, conj? }
//   смысл: `child` — это ВХОД для `parent` (ребёнок питает родителя)
// graph.options: настройки расчёта из открытого файла (нет — значения редактора)
```

Направление связи стоит запомнить, оно часто сбивает с толку: **ребёнок питает
родителя**. Рисуется линия от нижнего порта ребёнка (источника сигнала) вниз
к родителю (потребителю) — так же, как пользователь её тянет: от порта
источника к узлу, который этот сигнал принимает. Данные текут сверху вниз,
вершина оказывается внизу.

Поле `dist` хранится **в том же виде, в каком уйдёт на сервер**. Отдельной
модели представления нет, преобразование при отправке минимально (`cleanDist`).
Это заметно упрощает и сериализацию, и загрузку примеров.

## Сохранение

```js
function save() {
  const s = JSON.stringify(graph);
  try { localStorage.setItem("cra.graph", s); } catch (e) {}
  record(s);
}
```

`save()` вызывается из `render()`, то есть после **каждого** изменения. Схема
переживает перезагрузку страницы и случайно закрытую вкладку. Пустой `catch` —
на случай, если хранилище переполнено или запрещено политикой браузера: не
сохранилось, но работать не мешает. Та же строка JSON становится шагом истории
правок (`record`, см. следующий раздел).

При загрузке восстанавливается и счётчик идентификаторов:

```js
seq = graph.nodes.reduce((m, n) => Math.max(m, idNum(n.id)), 0);
```

Иначе после перезагрузки новый узел получил бы имя `n1`, уже занятое.

## Отмена и повтор

Ctrl+Z отменяет правку схемы, Ctrl+Y (или Ctrl+Shift+Z) повторяет отменённое.
То же делают кнопки «↶ Отменить» и «↷ Повторить» в палитре; кнопка гаснет,
когда отменять или повторять нечего.

Шаг истории — **снимок всей схемы**, а не описание операции:

```js
const hist = { undo: [], redo: [], cur: null };   // cur — снимок текущей схемы

function record(s) {
  if (s === hist.cur || historyHeld()) return;
  if (hist.cur !== null) hist.undo.push(hist.cur);   // не больше HISTORY_LIMIT = 100
  hist.redo.length = 0;   // новая правка обрывает ветку отменённого
  hist.cur = s;
}
```

Почему снимки, а не «команды» с парой «сделать/отменить» на каждую операцию.
Правок в редакторе десятки видов: узлы, связи, тип дуги, переименование,
распределения, марковское окно, смена типа модели, «Очистить», открытие файла.
Для каждой пришлось бы писать и поддерживать обратную операцию, и любая забытая
сломала бы историю. Снимок же делает `save()`, через который проходит **любая**
правка, — новые операции попадают в историю сами. Строку JSON `save()` всё
равно строит для `localStorage`, так что шаг почти ничего не стоит, а сравнение
строк сразу отсекает «правки», которые ничего не изменили (`id` уже занят,
введено не число).

Что шага **не** создаёт: выделение, сдвиг и масштаб холста, тип новой дуги,
имя файла, поле «t». Всё это не входит в `graph` — снимок не меняется.

Отмена и повтор — переход к соседнему снимку:

```js
function step(from, to, msg) {
  if (!from.length || historyHeld()) return;
  to.push(hist.cur);
  hist.cur = from.pop();
  graph = JSON.parse(hist.cur);
  …   // счётчик id, выделение, селектор типа модели, палитра
  buildPalette(); renderInspector(); render(); renderHistory();
  setStatus(msg, "ok");   // «правка отменена» / «правка повторена»
}
```

`render()` внутри `step` снова вызывает `save()`, но новой правкой это не
считается: `JSON.stringify(JSON.parse(s))` для таких данных даёт ту же строку
`s`, и `record` её пропускает. Выделение сохраняется, если выделенный узел или
дуга есть и в восстановленной схеме. Шаг мог отменить смену типа модели,
поэтому палитра перестраивается. Строка статуса сообщает, что правка отменена
или повторена: прежнее сообщение там (скажем, «пример загружен») могло
относиться как раз к отменённой правке.

**Один жест — один шаг.** Пока узел тащат, `render()` вызывается на каждое
движение мыши. Если бы каждое из них становилось снимком, одно перетаскивание
съело бы всю историю. Поэтому запись приостановлена:

```js
function historyHeld() {
  return (drag && drag.mode === "node") || !$("mk-modal").classList.contains("hidden");
}
```

Обработчик `mouseup` обнуляет `drag` **до** своего `render()`, и это
перемещение записывается одним шагом. Так же и марковское окно: правки в нём
сохраняются в `localStorage` сразу, а в историю попадают одним шагом при
закрытии окна. Пока окно открыто, Ctrl+Z ничего не делает.

**Отрисовка не должна менять схему.** Иначе простой выбор узла становился бы
«правкой», которую нечем отменить. Единственным таким местом был марковский
узел: инспектор приводил его к полной форме (у переходов `dist` вместо краткого
`rate`, у состояний координаты). Теперь это делает `normalizeGraph()` сразу,
как схема попала в редактор, — в `load()` и `documentToGraph()`.

История живёт только в памяти вкладки: после перезагрузки страницы она пуста,
сама схема восстанавливается из `localStorage`. Предел в сто шагов держит
память в рамках: снимок схемы из сотни узлов весит около 11 КБ, так что вся
история — порядка мегабайта, а для схемы из тысячи узлов — порядка десяти.

## Отрисовка

```js
function render() {
  $("viewport").setAttribute("transform", `translate(${view.tx},${view.ty}) scale(${view.s})`);
  renderEdges();
  renderNodes();
  save();
}
```

Стратегия — **полная перерисовка**: слои очищаются (`layer.textContent = ""`) и
строятся заново.

Для React-подобного мышления это расточительно, но здесь оправдано: схемы
надёжности содержат десятки, редко сотни узлов; полная перерисовка занимает
доли миллисекунды. Взамен исчезает целый класс ошибок «на экране не то, что в
данных» — картинка всегда является функцией от `graph`.

### Узел

```js
const g = document.createElementNS(SVGNS, "g");
g.setAttribute("class", "node " + nodeKind(n) + (selNodes.has(n.id) ? " selected" : "") + (n.top ? " top" : ""));
g.setAttribute("transform", `translate(${n.x},${n.y})`);
g.dataset.id = n.id;
```

`nodeKind(n)` возвращает роль, а для узла СФЦ без элемента (`dist: null`)
добавляет класс `fictive`: фиктивный узел рисуется полым и пунктирным, реальный —
сплошным (см. [`style.css`](web-style-css.md)). Та же функция даёт класс образцу
на кнопке палитры, так что кнопка и узел на холсте выглядят одинаково.

`createElementNS` с пространством имён SVG обязателен: `createElement("rect")`
создал бы элемент HTML, который не отрисуется внутри `<svg>`.

Состояние выражается **классами**, а не стилями напрямую, — оформление целиком
в [`style.css`](web-style-css.md).

`g.dataset.id` кладёт идентификатор прямо в DOM, и обработчик события находит
узел так:

```js
const nodeG = ev.target.closest(".node");
const id = nodeG.dataset.id;
```

`closest()` поднимается вверх по дереву, поэтому неважно, попал ли клик в
прямоугольник, в подпись или в порт.

### Связь

Каждая связь рисуется **двумя** путями:

```js
const hit = …;  hit.setAttribute("class", "edge-hit");   // невидимый, толстый
const path = …; path.setAttribute("class", "edge" + …);  // видимый, тонкий
```

Видимая линия толщиной 2 пикселя, попасть в неё мышью тяжело. Поэтому под ней
лежит прозрачная линия толщиной 12 пикселей (`.edge-hit { stroke: transparent;
stroke-width: 12; }`), которая и принимает клики. Стандартный приём для
интерактивной векторной графики.

`data-edge` стоит на **обоих** путях. Видимая линия нарисована позже и лежит
поверх зоны попадания, так что клик точно по ней достаётся ей. Без своего
`data-edge` такой клик не находил бы дугу и уходил в панораму, то есть снимал
выделение.

Shift+клик по дуге СФЦ сначала присваивает ей тип из инструмента «Новая дуга»
(см. ниже), а затем выделяет её, как обычный клик.

Форма — кубическая кривая Безье:

```js
function edgePath(a, b) {
  const dy = Math.max(24, Math.abs(b.y - a.y) / 2);
  return `M${a.x},${a.y} C${a.x},${a.y + dy} ${b.x},${b.y - dy} ${b.x},${b.y}`;
}
```

Управляющие точки смещены по вертикали, поэтому линия выходит из родителя вниз
и входит в ребёнка сверху — получается «ортогональный» вид, привычный по
схемам. `Math.max(24, …)` не даёт кривой выродиться в прямую при близких узлах.

Метки на дугах СФЦ несут вид дуги:

```js
const badge = (e.conj ? "&" : "≥1") + (e.inverse ? " ¬" : "");
```

Прямо на схеме видно, конъюнктивная дуга или дизъюнктивная и не инверсная ли
она, — без необходимости выделять её и смотреть в инспектор.

## Работа мышью

Единый обработчик `mousedown` определяет намерение по цели клика:

```js
if (portId)            drag = { mode: "connect", … };   // тянем новую связь
else if (nodeG)        drag = { mode: "node", … };      // двигаем узел (или группу)
else if (edgeId)       selectEdge(p, c);                // выделяем дугу
else if (ev.shiftKey)  drag = { mode: "frame", … };     // рамка выделения
else                   drag = { mode: "pan", … };       // панорама холста
```

Затем `mousemove` и `mouseup` на **window**, а не на холсте:

```js
window.addEventListener("mousemove", (ev) => { … });
```

Это существенно: если бы обработчик висел на SVG, то уход курсора за пределы
холста во время перетаскивания «терял» бы узел. Слушая окно, мы получаем
события везде.

### Различение клика и перетаскивания

```js
drag = { mode: "node", id, w0, start, toggle, sx: ev.clientX, sy: ev.clientY, moved: false };
…
if (!drag.moved && Math.abs(ev.clientX - drag.sx) + Math.abs(ev.clientY - drag.sy) <= 3) return;
…
if (!d.moved) { if (d.toggle) toggleNode(d.id); else select(d.id); }   // клик = выделение
```

Порог в 3 пикселя: рука дрожит, и без него простой клик по узлу нередко
превращался бы в микроперемещение — выделение не срабатывало бы, а в истории
правок появлялся бы шаг «сдвинул узел на пиксель». Тот же порог отличает клик
по пустому месту (снять выделение) от панорамы.

### Экран → мир

```js
function screenToWorld(sx, sy) {
  const r = $("canvas").getBoundingClientRect();
  return { x: (sx - r.left - view.tx) / view.s, y: (sy - r.top - view.ty) / view.s };
}
```

Обратное преобразование к тому, что применено к `#viewport`: вычесть положение
холста на странице, вычесть сдвиг, разделить на масштаб. Без него узел при
перетаскивании на увеличенном холсте «убегал» бы от курсора.

### Масштаб к курсору

```js
const wx = (mx - view.tx) / view.s, wy = (my - view.ty) / view.s;
view.s = Math.min(3, Math.max(0.2, view.s * factor));
view.tx = mx - wx * view.s; view.ty = my - wy * view.s;
```

Точка мира под курсором запоминается до изменения масштаба, а сдвиг после
подбирается так, чтобы она осталась под курсором. Именно так работает
масштабирование во всех картографических и графических программах: увеличение
идёт «в то место, куда смотришь», а не в центр экрана.

## Несколько узлов: выделить, сдвинуть, удалить

Выделение — множество идентификаторов, а не один:

```js
let selNodes = new Set();
function select(id) { selectNodes(id ? [id] : []); }   // ровно один узел или ничего
function toggleNode(id) { … }                          // добавить или убрать один
```

Как собрать выделение:

- **Ctrl+клик или Shift+клик по узлу** добавляет его к выделению, повторный —
  убирает (`toggleNode`). Модификатор запоминается в `drag.toggle` ещё на
  `mousedown`, а срабатывает на `mouseup`, если узел не сдвинули.
- **Shift+тянуть по пустому месту** — рамка: к выделению добавляются узлы,
  целиком попавшие в неё (см. ниже).
- **Ctrl+A** выделяет все узлы.
- **Esc** и клик по пустому месту снимают выделение. Ctrl+клик мимо узла
  выделение не сбрасывает (`drag.keep`): промах не должен стоить набранной
  группы.

Выделение дуги и выделение узлов взаимоисключающие: клик по дуге сбрасывает
узлы, клик по узлу — дугу. Обе операции над выделенным (сдвинуть, удалить)
относятся либо к узлам, либо к одной дуге.

**Рамка.** Простое перетаскивание по пустому месту — это панорама, к ней все
привыкли, поэтому рамка включается Shift. Shift и здесь значит «добавить»: рамка
добавляет узлы к уже выделенным (`drag.base`), так что группу можно набрать
несколькими рамками. Узел попадает в выделение, только если лежит в рамке
**целиком**:

```js
if (n.x >= x0 && n.y >= y0 && n.x + NODE_W <= x1 && n.y + NODE_H <= y1) selNodes.add(n.id);
```

Критерий «задет углом» выглядит щедрее, но в плотной схеме рамка через середину
то и дело цепляла бы соседей, и выделенное приходилось бы потом
вычищать Ctrl+кликами. Рамку можно тянуть в любую сторону — углы
нормализуются через `Math.min`/`Math.max`. Координаты сравниваются в мировой
системе (`screenToWorld`), поэтому рамка работает на любом масштабе и сдвиге.

Выделение пересчитывается на каждое движение мыши, и подсвечиваются узлы,
которые попадут в рамку, — это видно ещё до отпускания кнопки. Перерисовываются
при этом только узлы; инспектор строится один раз, на `mouseup`. Сама рамка —
временный `<rect class="sel-frame">` в `#temp-layer`, как и тянущаяся дуга.
Рамка меняет только выделение и шагов истории не создаёт.

**Перетаскивание группы.** Узел из выделения тащит за собой все выделенные,
невыделенный — только себя:

```js
const ids = selNodes.has(id) ? [...selNodes] : [id];
drag = { mode: "node", id, w0: screenToWorld(ev.clientX, ev.clientY),
  start: ids.map((k) => { const n = nodeById(k); return { n, x: n.x, y: n.y }; }), … };
…
const dx = w.x - drag.w0.x, dy = w.y - drag.w0.y;
for (const p of drag.start) { p.n.x = p.x + dx; p.n.y = p.y + dy; }
```

Смещение отсчитывается от **исходных** позиций, запомненных на `mousedown`, а не
прибавляется к текущим на каждое движение мыши. Так ошибки округления не
накапливаются, и вся группа гарантированно сдвигается на одно и то же
расстояние. Перемещение группы, как и одного узла, — один шаг истории.

**Удаление.** Одна функция на все случаи — Del, кнопка «Удалить узел» в
инспекторе и «Удалить выделенные» для группы:

```js
function deleteNodes(ids) {
  const gone = new Set(ids);
  graph.nodes = graph.nodes.filter((n) => !gone.has(n.id));
  graph.edges = graph.edges.filter((e) => !gone.has(e.parent) && !gone.has(e.child));
  …
}
```

Вместе с узлами уходят все их связи, входящие и исходящие: висячая связь на
несуществующий узел сломала бы и отрисовку, и запрос. Удаление группы — одна
правка, то есть один шаг истории: Ctrl+Z возвращает все узлы и связи разом.
Строка статуса так и напоминает: «удалено узлов: 5 (Ctrl+Z — вернуть)».

## Защита от циклов

```js
function addEdge(parent, child) {
  if (parent === child) return;
  if (graph.edges.some((e) => e.parent === parent && e.child === child)) return;
  if (reaches(child, parent)) { setStatus("нельзя: возникнет цикл", "err"); return; }
  …
}

function reaches(from, to) {
  const seen = new Set(); const st = [from];
  while (st.length) {
    const v = st.pop();
    if (v === to) return true;
    if (seen.has(v)) continue; seen.add(v);
    for (const e of childrenEdges(v)) st.push(e.child);
  }
  return false;
}
```

Обход в глубину: достижим ли `parent` из `child`? Если да, новая связь замкнула
бы цикл.

Проверка дублирует ту, что делает [`io.rs`](core-io-rs.md) на сервере, — и это
правильно. Серверная проверка обязательна (клиенту доверять нельзя), клиентская
нужна для удобства: пользователь узнаёт о проблеме в момент действия, а не
после расчёта.

Отдельно проверяется, что у элемента «НЕ» не больше одного входа.

## Инструмент «Новая дуга» (СФЦ)

В канонической СФЦ тип задаётся на каждой дуге: конъюнктивная (И) или
дизъюнктивная (ИЛИ), выход прямой или инверсный. Если каждую нарисованную дугу
приходится потом выделять и переключать в инспекторе, длинная серия
конъюнктивных входов превращается в рутину. Поэтому тип следующей дуги
выбирается заранее, как цвет кисти в графическом редакторе:

```js
let arcStyle = { conj: false, inverse: false };   // изначально ИЛИ, прямой
…
if (graph.kind === "sfc") applyArcStyle(e);       // в addEdge
```

- **Где выбрать.** Блок «Новая дуга» в палитре (`#arc-tool`): две пары кнопок,
  тип и выход, на каждой образец линии. Те же четыре кнопки на клавишах
  1–4 (1 — ИЛИ, 2 — И, 3 — прямой, 4 — инверсный). Блок и клавиши есть только
  в СФЦ: в дереве отказов вид входа задаёт логический элемент, а не дуга.
- **Что видно при рисовании.** Тянущаяся дуга уже имеет окончание
  будущей дуги (стрелка или точка) и метку `≥1` / `&` / `¬` у курсора.
  Сделать дугу «не той» и не заметить нельзя.
- **Как поправить готовые дуги.** Shift+клик по дуге присваивает ей текущий
  тип — так серию дуг можно перекрасить, не открывая инспектор. Инспектор
  по-прежнему меняет тип одной выделенной дуги.
- **Где хранится.** `arcStyle` — настройка редактора, а не схемы. В документ и
  в запрос она не попадает и лежит отдельно в `localStorage` под ключом
  `cra.arc`. Поэтому выбор переживает «Очистить», открытие файла и
  перезагрузку страницы.

`renderArcTool()` подсвечивает выбранные кнопки по их атрибуту:
`data-arc="conj:1"` горит, когда `arcStyle.conj === true`. Он вызывается из
`buildPalette()`, поэтому блок появляется и прячется вместе со сменой типа
модели.

## Инспектор

`renderInspector()` строит панель свойств заново при каждом изменении
выделения. Набор полей зависит от роли узла:

| Роль | Поля |
|---|---|
| `event` | идентификатор, распределение, «вершинное событие» |
| `gate` | идентификатор, операция, k (для «K из N»), «вершинное событие» |
| `sfc` | идентификатор, флажок «есть элемент», распределение, «вершина (критерий)» |
| дуга | тип (И/ИЛИ), выход (прямой/инверсный) — только для СФЦ |
| несколько узлов | их идентификаторы, число связей, которые уйдут вместе с ними, «Удалить выделенные» |

Общих свойств у группы узлов нет (у события распределение, у элемента
операция), поэтому панель группы ничего не редактирует. Она показывает, что
именно выделено, — первые 60 идентификаторов, остальные числом, — и удаляет
выделенное целиком (`renderGroupInspector`).

Поля распределений строятся по таблице:

```js
const DIST_SCHEMA = {
  fixed:       [["q", "q (вероятность отказа)", 0.01]],
  exponential: [["lambda", "λ (интенсивность)", 1e-4], ["mu", "μ (ремонт, опц.)", "", true]],
  weibull:     [["shape", "форма (k)", 2], ["scale", "масштаб (λ)", 10000]],
  …
};
```

Каждая запись — `[ключ, подпись, умолчание, необязательное?]`. Добавление
нового распределения — это одна строка здесь плюс одна в `DIST_NAMES`; форма
редактирования строится сама. Четвёртый элемент помечает `mu` как
необязательный, и пустое поле означает «удалить параметр» — то есть переход от
`ExponentialRepair` обратно к `Exponential`.

Постоянная вероятность — исключение: число одно, но это либо вероятность
отказа `q`, либо вероятность успеха `p = 1 − q`, как решит узел. В `dist` лежит
ровно одно из двух полей (движок понимает оба), `probKey(d)` говорит какое, а
`distFields(d)` подставляет его вместо строки таблицы — и форма, и `cleanDist`
берут поля оттуда. Выбор «Задана как» в инспекторе и галочка «успех p у всех
узлов» в палитре переключают вид через `setProbKey`, пересчитывая число
(`complement` округляет 1 − x до 15 знаков: 1 − 0.7 ≠ 0.3 в double), поэтому
расчёт от переключения не меняется. Галочка заодно задаёт `graph.prob` — вид
для новых узлов; если узлы расходятся с ним, она в состоянии «частично».

Переименование узла аккуратно обновляет и связи:

```js
for (const e of graph.edges) {
  if (e.parent === old) e.parent = v;
  if (e.child === old) e.child = v;
}
```

Связи хранят идентификаторы, а не ссылки, поэтому переименование требует явного
обхода.

## Редактор марковской диаграммы

Отдельный маленький редактор внутри модального окна, устроенный по тем же
принципам: состояния — окружности, переходы — кривые со стрелками, порт для
вытягивания нового перехода, панель свойств справа.

### Начальная раскладка по кругу

```js
states.forEach((s, i) => {
  const a = (i / Math.max(1, states.length)) * 2 * Math.PI - Math.PI / 2;
  d._pos[s] = { x: cx + R * Math.cos(a), y: cy + R * Math.sin(a) };
});
```

Состояния без заданных координат расставляются по окружности — при небольшом их
числе это даёт разумную и читаемую картинку сразу.

Координаты хранятся в `d._pos` внутри самого объекта распределения. Подчёркивание
в имени — соглашение «служебное поле»; функция `cleanDist` его при отправке
отбрасывает, поэтому на сервер оно не попадает.

### Разведение встречных переходов

```js
const hasReverse = (d.transitions || []).some((t) => t.from === tr.to && t.to === tr.from);
const off = hasReverse ? 16 : 0;
const px = -uy * off, py = ux * off;
```

Если есть обратный переход (отказ и восстановление), обе дуги смещаются на 16
пикселей перпендикулярно линии — иначе они наложились бы и стали неразличимы.
`(-uy, ux)` — вектор, перпендикулярный единичному `(ux, uy)`.

### График q(t) — считает сервер

Самый интересный приём во всём файле:

```js
const req = {
  model: { type: "fault_tree", top: "x",
           events: [{ id: "x", dist: cleanDist(d) }], gates: [] },
  times
};
const r = await fetch("/api/analyze", { method: "POST", … });
```

Чтобы нарисовать кривую вероятности отказа марковского узла, интерфейс
**заворачивает этот узел в крошечное дерево отказов из одного события** и
отправляет на обычный `/api/analyze` с 60 моментами времени.

Ценность решения в том, чего он позволяет **не** делать: не нужно
реализовывать uniformization и уравнения марковского восстановления на
JavaScript. График показывает ровно то, что посчитает движок, и разойтись они
не могут в принципе. Численного кода в браузере нет вовсе.

Шестьдесят точек стоят почти столько же, сколько одна, — структура строится
один раз (см. [`analysis.rs`](core-analysis-rs.md)).

Верхняя граница времени по умолчанию берётся из самих часов:

```js
function mkSuggestTmax() {
  let m = 0;
  for (const tr of MK.dist.transitions || []) m = Math.max(m, jsClockScale(tr.dist));
  return m > 0 ? m * 3 : 1000;
}
```

Три характеристических масштаба самого медленного перехода — диапазон, в
котором кривая успевает показать своё поведение.

### Рисование графика — `drawChart`

`drawChart(svg, st, pts, xmax, opts)` строит оси, сетку, линию и подпись
конечного значения вручную в SVG. Это общий компонент: тот же график рисует и
кривую вероятности системы в результатах. Каждый график держит своё состояние
`st` (точки `{t, v}` и геометрию) для подсказки, а слой подсказки ищется
внутри своего `svg` (`.ch-overlay`), так что графиков на странице может быть
несколько. Параметры `opts`:

- `ymax` — верх оси значений. Марковский узел — это вероятность от 0 до 1,
  ему `ymax: 1`. Вероятность отказа системы часто порядка 10⁻³, и на оси 0…1
  кривая слиплась бы с нулём, поэтому для неё верх берёт `niceMax` — ближайшее
  сверху «круглое» 1, 2, 4 или 8 × 10ᵏ (шаг сетки — четверть, тоже круглый);
- `name` — буква значения в подсказке (`q` или `P`);
- `marks` — моменты, отмеченные кружками на линии.

Подписи делений проходят через `toPrecision(6)`: иначе 3 × 0,1 дало бы на оси
«0.30000000000000004».

Оформительские решения заслуживают упоминания:

- сетка приглушена, ось нуля выделена — данные важнее разметки;
- **прямая подпись** последней точки вместо легенды: ряд один, легенда была бы
  лишним посредником;
- при наведении показывается перекрестие и подсказка `t=… q=…`, причём она
  переворачивается влево у правого края, чтобы не выйти за границу:

```js
let bx = cx + 8; if (bx + tw > g.W - g.R) bx = cx - 8 - tw;
```

Подсказка берёт момент под курсором из геометрии, которую запомнил
`drawChart`: `t = xmax · (mx − L) / (W − L − R)`. До выделения общего
компонента `xmax` читался из `geom`, где его не было, получалось `NaN`, и
подсказка всегда показывала первую точку (t = 0), где бы ни стоял курсор.

## Сериализация: граф → запрос

`graphToRequest()` собирает JSON и **одновременно** список ошибок:

```js
const errs = [];
if (!graph.nodes.length) errs.push("схема пуста");
…
if (kids.length) errs.push(`событие «${n.id}» не может иметь входов`);
if (!kids.length) errs.push(`у элемента «${n.id}» нет входов`);
if (g.k > kids.length) errs.push(`«${n.id}»: k=${g.k} больше числа входов`);
```

Собираются **все** ошибки, а не только первая, и показываются списком:

```js
showError("Схема неполна:\n• " + errs.join("\n• "));
```

Гораздо лучше, чем исправлять по одной ошибке за запуск.

### Определение вершины

```js
function findTop() {
  const isChild = new Set(graph.edges.map((e) => e.child));
  const isParent = new Set(graph.edges.map((e) => e.parent));
  const rootCandidates = graph.nodes.filter((n) => isParent.has(n.id) && !isChild.has(n.id));
  const marked = graph.nodes.filter((n) => n.top);
  if (marked.length === 1) return { top: marked[0] };
  if (marked.length > 1) return { top: null, err: "отмечено несколько вершинных узлов" };
  if (rootCandidates.length === 1) return { top: rootCandidates[0] };
  if (graph.nodes.length === 1) return { top: graph.nodes[0] };
  return { top: null, err: "не удаётся определить вершину — отметьте её галочкой в инспекторе" };
}
```

`graphToRequest` кладёт `err` в список ошибок запроса; подсветка набора на
схеме (см. ниже) по той же функции узнаёт, дошло ли состояние до вершины.

Иерархия правил: явная отметка важнее автоопределения; автоопределение работает,
только если кандидат единственный; в неоднозначном случае — понятная просьба, а
не произвольный выбор.

Кандидат в вершины — узел, у которого есть входы, но который сам никуда не
входит.

### `cleanDist`

```js
for (const [k, , , opt] of DIST_SCHEMA[d.type]) if (d[k] != null && d[k] !== "") o[k] = +d[k];
```

Оставляет только поля, относящиеся к выбранному типу, и приводит их к числу
через унарный `+`. Поля от ранее выбранного распределения и служебные (`_pos`)
не попадают в запрос.

Для марковских узлов есть отдельная ветка, которая сворачивает экспоненциальные
переходы к краткой форме `rate`:

```js
if (dist.type === "exponential") return { from: tr.from, to: tr.to, rate: +dist.rate };
```

Запрос получается компактнее и совпадает с формой, принятой в примерах.

## Документ: схема ⇄ JSON

Схема хранится на диске и показывается во вкладке JSON в одном и том же виде —
**документ**. Это обычный запрос на расчёт, к которому добавлено поле `layout`
с координатами:

```json
{
  "model": { "type": "sfc", "nodes": [ … ], "criterion": { "target": "sink" } },
  "mission_time": 0,
  "options": { "cut_sets": true, "path_sets": true },
  "layout": {
    "nodes":  { "src": { "x": 60, "y": 60 }, "left1": { "x": 232, "y": 172 } },
    "markov": { "left1": { "ok": { "x": 300, "y": 50 }, "fail": { "x": 300, "y": 350 } } }
  }
}
```

Движок поле `layout` не читает: serde по умолчанию пропускает незнакомые поля.
Поэтому сохранённый из браузера файл без переделки считается и из командной
строки — `cra схема.json`. Чтобы никто случайно не сломал это, добавив
`deny_unknown_fields`, есть тест `editor_layout_field_is_ignored` в
[`tests/integration.rs`](core-tests-rs.md).

`layout.markov` хранит положения состояний марковских узлов (в редакторе они
лежат в `dist._pos`, а `cleanDist` их в модель не пропускает). Координаты
округляются до целых — дробные пиксели только раздували бы файл.

### Граф → документ

```js
function graphToDocument() {
  const { req, errs } = graphToRequest();
  req.layout = graphLayout();
  return { doc: req, errs };
}
```

Вся логика сборки модели остаётся в `graphToRequest` — документ отличается
только добавленной раскладкой. Настройки расчёта из открытого файла
(`graph.options`) переживают цикл «открыл → поправил → сохранил»; если файла не
было, подставляются значения редактора.

### Документ → граф

`documentToGraph(doc)` делит проблемы на два сорта:

- **структурные** — не тот тип модели, повтор идентификатора, неизвестное
  распределение или операция. Такой граф редактор не сможет показать, поэтому
  бросается `Error`, а текущая схема не трогается;
- **поправимые** — вход ссылается на несуществующий узел, вход указан дважды,
  вершина не найдена, критерий СФЦ составной (`op`/`args`). Они собираются в
  `warns` и показываются в панели результатов. Битые связи отбрасываются: на
  экране их не было бы видно, а значит, не было бы и способа их удалить.

Принимается и «голая» модель без обёртки запроса (`{"type": "sfc", …}`).

### Авто-раскладка

Если координат в документе нет (написан руками, пришёл из другой программы),
`autoLayout` расставляет узлы по рядам — упрощённый алгоритм Сугиямы:

1. **Ряд** узла — длина самого длинного пути от него до стока. Вершина внизу,
   каждый узел на ряд выше самого нижнего из своих потребителей, и все дуги
   идут сверху вниз, как их рисует `renderEdges`. Ряды считаются алгоритмом
   Кана от стоков, без рекурсии: глубокая схема не переполнит стек браузера, а
   узлы на цикле просто остаются в ряду 0 (такую схему всё равно отвергнет
   движок).
2. **Порядок в ряду** — восемь проходов по барицентрам: узел сдвигается к
   среднему положению своих соседей, попеременно по входам (сверху вниз) и по
   потребителям (снизу вверх). Это заметно сокращает пересечения дуг.

Схема из 4000 узлов раскладывается за ~0,3 с.

Если координаты есть лишь у части узлов (в файл дописали узел руками),
сохранённые положения берутся как есть, а остальные узлы получают позиции из
авто-раскладки, сдвинутые вправо от уже расставленных, — чтобы не лечь поверх.

### Вкладка JSON

```js
let jsonEdited = false;
function setJsonText(doc) { $("input").value = JSON.stringify(doc, null, 2); jsonEdited = false; }
```

При переходе на вкладку JSON текст заново строится из схемы — **если его не
правили руками** (событие `input` ставит `jsonEdited = true`). Так вкладка
всегда показывает актуальную схему, но ручная правка не теряется от простого
переключения вкладок. «◀ Из схемы» перестраивает текст принудительно, «В
схему ▶» делает обратное: разбирает текст и заменяет им диаграмму.

## Файлы: сохранить и открыть

Страница не может писать на диск сама. Сохранение — это загрузка файла,
созданного в памяти:

```js
const url = URL.createObjectURL(new Blob([text], { type: "application/json" }));
const a = el("a", { href: url, download: name });
document.body.append(a);   // Firefox нажимает только ссылки, стоящие в документе
a.click();
```

Куда ляжет файл — в папку загрузок или через диалог «Сохранить как», — решают
настройки браузера. Имя берётся из поля рядом с кнопками (`.json` дописывается
сам); после открытия файла там его имя, и оно переживает перезагрузку
страницы (`localStorage`, ключ `cra.file`).

Сохраняется **то, что видно**: на вкладке «Схема» — документ схемы, на вкладке
JSON — текст как есть (только проверяется, что это JSON). Неполную схему
сохранить можно — это незаконченная работа; статус лишь предупредит.

Открытие — скрытый `<input type="file">`, по нажатию кнопки или Ctrl+O. После
выбора значение поля сбрасывается, иначе повторный выбор того же файла не
вызвал бы `change`. Дальше `file.text()` → `JSON.parse` → `applyDocument`:
граф заменяется, переключается вкладка «Схема» (скрытый холст имеет нулевой
размер, и `fitView` промахнулся бы), старые результаты сбрасываются — они
относились к прежней схеме.

## Запуск расчёта и показ результата

```js
async function analyze() {
  let payload;
  if ($("tab-json").classList.contains("active")) {
    payload = JSON.parse($("input").value);
  } else {
    const { req, errs } = graphToRequest();
    if (errs.length) { showError(…); return; }
    payload = req;
    setJsonText(graphToDocument().doc);   // синхронизируем вкладку JSON
  }
  payload.options = Object.assign({}, payload.options, calcOptions());   // галочки «Считать»
  …   // кривая P(t): к моментам запроса добавляется сетка (см. ниже)
  …
  const r = await fetch("/api/analyze", { … });
  const data = await r.json();
  if (!r.ok) { showError(data.error || "HTTP " + r.status); … }
  renderResponse(data, view);   // тип модели, сколько моментов «своих», есть ли кривая
  setStatus("готово за " + Math.round(performance.now() - t0) + " мс", "ok");
}
```

Три полезные детали:

- расчёт из вкладки «Схема» попутно заполняет вкладку JSON — видно, что именно
  ушло на сервер (плюс `layout`, который серверу не отправляется), и это заодно
  хороший способ изучить формат;
- кнопка блокируется на время запроса (`$("analyze").disabled = true`) в
  `try/finally`, поэтому разблокируется даже при ошибке;
- показывается фактическое время ответа.

Что считать, кроме вероятности вершины, решают галочки «Считать» (см.
следующий раздел). `Object.assign` кладёт их *поверх* опций запроса, так что
они действуют на любой вкладке — и для JSON, набранного руками.

## «Считать» — что просить у сервера

В шапке панели результатов — галочки: **сечения**, **пути**, **значимость**,
**ROBDD**, **график P(t)**. Первые четыре — флаги `cut_sets`, `path_sets`,
`importance` и `bdd` запроса; вероятность вершины считается всегда. Изначально
включено всё. Лишнее стоит выключать: пути — это второй полный расчёт по
двойственной формуле, а на большой схеме и сечения, и выдача диаграмм заметно
удлиняют ответ. Меры значимости дёшевы — два прохода по каждой BDD.

Пятая галочка, **график P(t)**, — только интерфейс: она меняет моменты
времени в запросе (см. «Кривая P(t)» ниже), а в опции и в файл не попадает.
Поэтому в опции уходят не все флаги `calc`, а только флаги движка:

```js
let calc = { cut_sets: true, path_sets: true, bdd: true, importance: true, curve: true };
const CALC_ENGINE = ["cut_sets", "path_sets", "importance", "bdd"];
…
const req = { model, options: Object.assign({}, graph.options || { max_order: 8 }, calcOptions()) };
```

**Чья это настройка.** Редактора, а не схемы — как тип новой дуги. Выбор лежит
в `localStorage` под ключом `cra.calc` и переживает перезагрузку страницы,
«Очистить» и открытие файлов: флаги из открытого файла галочки не меняют. Так
один раз выбранное «что мне нужно от сервера» не сбивается каждой новой схемой.
Шагом истории правок смена галочки не считается.

**Что попадает в файл.** Сохранённый документ несёт флаги галочек явно (вместе
с пределами `max_order`, `cutoff` из открытого файла), поэтому
`cra схема.json` из командной строки посчитает ровно то же, что редактор.
Вкладка JSON показывает их же и обновляется сразу при щелчке по галочке, если
текст не правили руками.

**Вкладка JSON.** Галочки решают и там: при расчёте их флаги кладутся поверх
опций из текста. Иначе одна и та же галочка то действовала бы, то нет, смотря
по вкладке.

Показ результатов (`renderResponse`) выводит крупное значение вероятности,
таблицу по временам, кривую P(t), значимость элементов и диаграммы ROBDD (см.
ниже), таблицы сечений и путей с разбором (не более 200 строк — иначе браузер
захлебнётся на 20 000 наборов), предупреждения и статистику.

Кривая, значимость и ROBDD стоят сразу под таблицей вероятностей, а не под
списками наборов (там их было бы не найти), и сворачиваются. Это делает общий
помощник `foldSection(cls, key, title)`: раздел — `<details>`, а раскрыт ли он,
помнит `localStorage` под ключом `key` (`cra.curve`, `cra.imp`, `cra.bdd`), так
что свёрнутое однажды остаётся свёрнутым и после следующего расчёта.

### Кривая P(t)

С галочкой «график P(t)» в результатах — кривая вероятности вершины (в дереве
— отказа, в СФЦ — выполнения критерия) от 0 до наибольшего момента из поля
«t». Отдельного расчёта для неё нет: `analyze()` добавляет к моментам запроса
сетку из `CURVE_STEPS = 60` равных шагов (`curveGrid`, без моментов, которые
уже есть), и движок считает вероятность и в этих точках. Модули и BDD
строятся один раз на запрос, а каждая лишняя точка — лишь проход по BDD,
поэтому график почти ничего не стоит.

Порядок важен: **свои моменты идут первыми**, сетка — после.

```js
const base = payload.times … || [payload.mission_time];
payload.times = base.concat(curveGrid(base));
view.shown = base.length;   // таблица и KPI — только по ним
```

Наборы, значимость и ROBDD движок считает для первого момента списка. Если бы
сетка, начинающаяся с нуля, шла первой, всё это считалось бы для t = 0, где
почти ничего не успело отказать. `view.shown` говорит `renderResponse`, сколько
первых результатов — моменты пользователя: только они попадают в таблицу и
KPI, а график строится по всем точкам, отсортированным по времени. Моменты
пользователя отмечены на линии кружками (`marks`).

Рисует общий `drawChart` (см. «Рисование графика — `drawChart`»), верх оси
значений — `niceMax` над максимумом: вероятность отказа системы бывает порядка
10⁻³, и на оси 0…1 линия слиплась бы с нулём. График рисуется, когда у `svg`
есть размер: раздел может быть свёрнут, а панель результатов скрыта. Это
отслеживает `ResizeObserver` — он же перерисовывает график при изменении
ширины окна и отключается, когда результаты перестроены и `svg` удалён из
документа. При t = 0 кривой нет: строить её не на чем.

Если что-то запрошено галочкой, а в ответе этого нет, появляется
предупреждение «Запрошено, но сервер не вернул: …». Движок старой версии молча
пропускает незнакомые флаги, и без предупреждения раздел просто не появлялся
бы. Так бывает в режиме разработки: ассеты читаются с диска и уже новые, а
сервер запущен до пересборки движка.

Формат чисел:

```js
function fmtP(p) { if (p === 0) return "0"; return p >= 1e-3 ? p.toFixed(6) : p.toExponential(4); }
```

Обычные числа — с фиксированной точкой, малые — в экспоненциальной форме. Для
надёжности это существенно: значения вида `1.2e-9` встречаются постоянно, а
`0.000000` вместо них было бы бесполезно.

## Сечения и пути в результатах

`renderSets(report, which, kind)` рисует одну таблицу — сечений
(`which = "cut"`) или путей (`"path"`). Сервер отдаёт наборы по убыванию
вероятности, и таблица сохраняет этот порядок; номер строки (№) — место набора
в нём.

**Сечения.** P сечения — вероятность совместного отказа его элементов, сумма P
по всем сечениям — оценка Q сверху (`rare_event_approx`). От этой суммы
считаются два столбца:

| Столбец | Что это |
|---|---|
| Доля | P сечения / Σ P, в процентах; под числом полоска той же длины, как у FV |
| Накопл. | доля первых сечений до этого включительно; последняя строка — 100 % |

Строка над таблицей называет, сколько первых сечений дают 90 % суммы. Обычно
это несколько сечений из сотен — на них и стоит смотреть. Знаменатель — именно
сумма, а не точное Q: только тогда накопленная доля доходит ровно до 100 %.
При малых q разница между ними — доли процента; при больших сумма бывает и
больше единицы, а доли остаются осмысленными.

**Единичные отказы** (`singleFailures`) — сечения первого порядка: отказ такого
элемента в одиночку валит систему (в СФЦ — нарушает критерий). Они
перечислены отдельной строкой над таблицей, даже если стоят далеко не первыми
по вероятности. В примере СФЦ-моста это `src` с q = 0: отказать он сейчас не
может, но по структуре — единственная точка отказа. Если таких элементов нет,
строка говорит и об этом, но только при неусечённом списке: `max_order`,
`max_sets` или `cutoff` могли отбросить и сечение первого порядка, и тогда
утверждать «нет» нельзя.

**По порядку** (`ordersLine`) — сколько наборов каждого порядка и, у сечений,
какую долю суммы они дают: сечений высоких порядков обычно много, а риск — у
низких.

**Пути.** P пути — вероятность того, что исправны все его элементы. Сумма P
путей ни к чему не сводится (в примере дерева она больше пяти), поэтому у путей
нет ни долей, ни строки про 90 %; распределение по порядкам — без долей.

Строк в таблице — не больше `SETS_ROWS = 200`; остальное — строкой «показаны
первые 200 из N». Накопленная доля считается по всем наборам, так что и в
усечённой таблице она верна.

## Подсветка набора на схеме

Щелчок по строке сечения или пути подсвечивает набор на схеме; повторный
щелчок по той же строке, Esc или «✕» на плашке снимают подсветку. Видно не
только элементы набора, но и **куда доходит их состояние**: для сечения —
какие вентили (узлы СФЦ) отказывают вслед за его элементами и по каким дугам
отказ поднимается к вершине; для пути — какие узлы при нём работают.

Для этого схема вычисляется при одном конкретном состоянии элементов:

- сечение — отказали ровно его элементы, остальные исправны;
- путь — исправны ровно его элементы, остальные отказали.

`failedNodes(failed)` возвращает узлы в отказе при отказе элементов `failed`.
Логика та же, что у движка (`io.rs`):

- дерево — событие в отказе, если оно в `failed`; вентиль — по своей операции
  над входами (И, ИЛИ, XOR по чётности, НЕ, K из N, И-НЕ, ИЛИ-НЕ);
- СФЦ — узел работает, если исправен его элемент (у фиктивного узла элемента
  нет), сигнал доставляют все И-дуги и хотя бы одна ИЛИ-дуга (пустая группа не
  мешает); инверсная дуга доставляет сигнал, когда источник **не** работает.

Подсвечиваются узлы в том же состоянии, что и набор: у сечения — в отказе, у
пути — работающие (`hlState`: `src` — элементы набора, `hit` — узлы в этом
состоянии, `top` — дошло ли оно до вершины). Дуга подсвечена (`hlEdge`), если
по ней это состояние пришло в узел: оба её конца в нём. У инверсной дуги СФЦ и
у входа НЕ, И-НЕ, ИЛИ-НЕ — наоборот: источник не в этом состоянии. Так у
вентиля ИЛИ, отказавшего из-за одного входа, подсвечен только этот вход.

Плашка вверху холста (`renderHlBanner`) называет набор и итог:

| Набор | Вершина в том же состоянии | Иначе |
|---|---|---|
| сечение | «его отказ» или «их совместный отказ приводит к отказу системы» (в СФЦ — «нарушает критерий») | «до вершины отказ не доходит» |
| путь | «пока он исправен» или «пока они исправны, система не откажет» (в СФЦ — «…работоспособности достаточно для выполнения критерия») | «исправности не хватает» |

«Иначе» для набора из ответа сервера бывает в двух случаях: схему поправили
после расчёта или она немонотонна (с НЕ и XOR наборы приближённые). Плашка так
и говорит. Элементы набора, которых на схеме уже нет, перечислены в ней
отдельно.

**Подсветка живая.** Состояние вычисляется заново при каждой отрисовке
(`renderNodes`, `renderEdges`), а не запоминается при щелчке. Поэтому правка
схемы сразу видна на подсветке: например, сменить у «K из N» k с 2 на 3 — и
сечение из двух датчиков перестанет доходить до вершины, а отмена правки
вернёт как было. Пересчёт — один проход по узлам и дугам со словарями
`Map`, на отрисовку он не влияет. Сбрасывают подсветку новый расчёт (номера
наборов — из прежнего ответа), ошибка расчёта, открытие файла или примера,
«Очистить».

Ещё несколько деталей. Если хоть один элемент набора за краем видимой области
или под плашкой, `revealNodes` сдвигает холст, не меняя масштаба, так что
рамка набора встаёт в центр видимой части — под плашкой. Набор, который и так
виден, холст не двигает. Щелчок по строке при
открытой вкладке JSON переключает на схему: подсветка нужна, чтобы её видеть.
Выделение для правки работает и при подсветке, его рамка видна поверх цвета
подсветки. Выделение текста в таблице мышью (скопировать имена) щелчком по
строке не считается.

Сверка с движком — в браузерном тесте: на всех комбинациях отказов элементов
(q = 0 или 1, тогда вероятность вершины у движка ровно 0 или 1) для обоих
примеров, дерева со всеми видами вентилей и СФЦ с инверсными дугами и
фиктивным узлом `failedNodes` даёт то же состояние вершины, что сервер.

## Значимость элементов в результатах

Ответ с `options.importance` несёт для каждого базового события меры
значимости (как они считаются — в [core-analysis-rs.md](core-analysis-rs.md),
раздел «Меры значимости»). `renderImportance` показывает их таблицей:

| Столбец | Что это |
|---|---|
| q | вероятность отказа элемента |
| Бирнбаум | `∂Q/∂q` — чувствительность вероятности отказа системы к элементу |
| FV (критичность) | доля риска, связанная с элементом, в процентах; под числом полоска той же длины |
| RAW | во сколько раз вырастет Q, если элемент отказал |
| RRW | во сколько раз Q упадёт, если элемент безотказен; «∞» — элемент в одиночку держит систему |

Меры — в терминах отказа и для дерева, и для СФЦ, поэтому таблица читается
одинаково. Над ней — Q системы и момент времени (первый из списка).

**Сортировка.** Щелчок по заголовку столбца сортирует по нему по убыванию,
столбец «Элемент» — по алфавиту; выбранный столбец помечен «▾». Изначально —
по FV, как отдаёт сервер. Выбор живёт в `IMP.sort` и переживает следующий
расчёт. Бесконечный RRW (`null` при Q > 0) при сортировке считается
бесконечностью и встаёт наверх; неопределённые меры (при Q = 0) — вниз.

Строк — не больше 200, как у наборов; остальное — строкой «показаны первые
200 из N».

## ROBDD в результатах

Ответ с `options.bdd` несёт диаграммы решений, по которым движок посчитал
вероятность (формат — в [core-analysis-rs.md](core-analysis-rs.md), раздел
«ROBDD наружу»). Схема считается не целиком, а по независимым модулям: у
каждого модуля свой ROBDD, а вложенный модуль в нём — одна переменная.
`renderBdd` показывает их по одной:

- **Вкладки модулей** — от вершины вниз по вложенности (обход в ширину по
  переменным-модулям, `bddOrder`), на каждой имя модуля и число узлов.
- **Щелчок по узлу-модулю** (прямоугольник) открывает диаграмму этого модуля.
- **Подсказка** при наведении на узел: уровень, вероятность подфункции от этого
  узла и вероятность самой переменной. Вероятности — для первого момента
  времени, как у наборов.
- Раздел сворачивается (`foldSection`, ключ `cra.bdd`).
- Если модуль не влез в предел `bdd_max_nodes`, вместо рисунка — сообщение с
  его размером.

Обозначения — общепринятые для BDD: сплошная линия — ветка «переменная = 1»,
пунктир — «= 0», внизу листья 0 и 1. Подпись под заголовком переводит их на
язык модели: в дереве отказов «= 1» — событие произошло, лист 1 — вершинное
событие наступило; в СФЦ «= 1» — элемент работоспособен, лист 1 — критерий
выполнен (`kind` берётся из отправленного запроса).

### Раскладка — `drawBdd`

ROBDD упорядочена: на любом пути переменные идут в одном и том же порядке.
Поэтому рисунок послойный: строка — уровень (переменная), слева колонка с
именем переменной и её вероятностью, внизу строка листьев (0 слева, 1 справа).
Уровни, на которых узлов нет (переменная выпала из функции), не рисуются.

Главная трудность — **длинные ветки**. Ветка часто перескакивает через
несколько уровней (в цепочке ИЛИ каждая «= 1» ведёт прямо к листу 1), и,
нарисованная напрямую, проходит сквозь узлы промежуточных строк. Приём из
алгоритма Сугиямы: такая ветка получает «пустую» точку в каждой промежуточной
строке:

```js
for (let r = rowOf(n.id) + 1; r < rowOf(c); r++) {
  const k = n.id + cls + r;   // строка-ключ: у настоящих узлов ключи — числа
  rows[r].push(k); …
}
```

Пустые точки участвуют в раскладке наравне с узлами (ширина 6 px), поэтому
место для линии резервируется, и она обходит узлы. Порядок внутри строк — восемь
проходов по барицентрам соседей, попеременно сверху вниз и снизу вверх, как у
авто-раскладки схемы; листья не переставляются. Ветка рисуется кривыми Безье
через свои точки с вертикальной касательной в каждой, так что линия идёт
плавно. Из узла ветка «= 0» выходит чуть левее центра, «= 1» — чуть правее.

## Горячие клавиши

```js
if (e.key === "Escape" && !$("mk-modal").classList.contains("hidden")) closeMarkov();
else if (e.key === "Escape" && editorKeyAllowed(e)) { select(null); clearHl(); }
else if (mod && e.key === "Enter") analyze();
else if (mod && e.code === "KeyS") { e.preventDefault(); saveFile(); }
else if (mod && e.code === "KeyO") { e.preventDefault(); $("file-input").click(); }
else if (mod && e.code === "KeyZ" && editorKeyAllowed(e)) { e.preventDefault(); if (e.shiftKey) redo(); else undo(); }
else if (mod && e.code === "KeyY" && editorKeyAllowed(e)) { e.preventDefault(); redo(); }
else if (mod && e.code === "KeyA" && editorKeyAllowed(e)) { e.preventDefault(); selectNodes(graph.nodes.map((n) => n.id)); }
else if ((e.key === "Delete" || e.key === "Backspace") && editorKeyAllowed(e)) { e.preventDefault(); deleteSelection(); }
else if (ARC_KEYS[e.code] && arcKeyAllowed(e)) setArcStyle(ARC_KEYS[e.code]);
```

Escape закрывает модальное окно, а если оно закрыто — снимает выделение и
подсветку набора.
Ctrl+Enter (или Cmd+Enter) запускает расчёт из любого места, Ctrl+S сохраняет,
Ctrl+O открывает файл. Del (или Backspace) удаляет выделенные узлы со связями
либо выделенную дугу, Ctrl+A выделяет все узлы. Ctrl+Z отменяет правку схемы,
Ctrl+Y и Ctrl+Shift+Z повторяют. Клавиши 1–4 в СФЦ выбирают тип новой дуги.

Del слушается на `document`, а не на холсте. Раньше обработчик висел на
`#canvas` и срабатывал, только когда фокус был на холсте. Но `mousedown` по
узлу вызывает `preventDefault()` (иначе браузер начал бы выделять текст), и
фокус холст при этом не получает. Поэтому после клика по узлу, добавленному
кнопкой палитры, Del молча не работал, пока пользователь не щёлкнет по пустому
месту холста.

Клавиши редактора схемы проверяет `editorKeyAllowed`: они работают только на
вкладке «Схема», при закрытом марковском окне и не перехватываются, пока фокус
в поле ввода. Там у тех же клавиш своя работа: цифра, набранная в поле «t»,
остаётся вводом, а Ctrl+Z в поле отменяет набранный текст, а не правку схемы.
Галочка — исключение: своих клавиш, кроме пробела, у неё нет, и после щелчка по
галочке «Считать» или флажку инспектора Del и Ctrl+Z по-прежнему относятся к
схеме.
Цифрам (`arcKeyAllowed`) вдобавок нужны модель СФЦ и отсутствие модификаторов.

Для S, O, Z, Y, A и цифр проверяется `e.code` (физическая клавиша), а не `e.key`: в русской
раскладке `e.key` был бы «ы» и «щ», и сочетание молча не сработало бы. Цифры
по `e.code` тоже не зависят от раскладки, а вдобавок цифровой блок
(`Numpad1`…) работает так же, как верхний ряд.
`preventDefault()` не даёт браузеру открыть собственный диалог «Сохранить
страницу».
