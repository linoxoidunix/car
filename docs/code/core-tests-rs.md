# 9. `crates/cra-core/tests/integration.rs` — доказательства правильности

**Размер:** 295 строк. **Задача:** прогнать движок целиком, от текста JSON до
ответа, и сверить результат с числами, посчитанными вручную.

## Чем это отличается от тестов внутри модулей

В файлах `bdd.rs`, `dist.rs`, `markov.rs`, `module.rs` есть свои блоки
`#[cfg(test)] mod tests` — это **модульные тесты**: они видят приватные
функции и проверяют одну деталь.

`tests/integration.rs` лежит отдельно и видит только **публичный API**, как
любой внешний пользователь:

```rust
fn run(json: &str) -> cra::Response {
    let req: Request = serde_json::from_str(json).expect("request parses");
    cra::analyze_request(&req).expect("analysis succeeds")
}
```

Каждый тест — это строка JSON и утверждение о результате. Разбор JSON, сборка,
декомпозиция, BDD, minsol, свёртка — работает всё вместе или не работает
ничего.

Это заодно и лучшая документация формата: рабочие запросы, которые нельзя
оставить устаревшими, потому что они выполняются на каждой сборке.

## Тесты по одному

### `bridge_fault_tree` — мостиковая схема

Классическая задача теории надёжности. Мостиковая схема — простейшая схема,
которая **не сводится** к последовательно-параллельному соединению: её нельзя
посчитать, просто перемножая и складывая. Каноническая проверка любого движка.

Она задана деревом отказов из своих минимальных сечений `{1,2}`, `{4,5}`,
`{1,3,5}`, `{2,3,4}`, у всех элементов q = 0,1.

```rust
assert!((p - 0.02152).abs() < 1e-12);
```

Точное значение 0,02152 известно из литературы. Допуск `1e-12` — это заявление:
ответ **точный**, а не приближённый; расхождение только на уровне округления
double.

Проверяется и структура сечений:

```rust
assert_eq!(cuts.count, 4);
assert_eq!(orders, vec![2, 2, 3, 3]);
assert!((cuts.sets[0].probability - 0.01).abs() < 1e-15);
```

Ровно четыре сечения (никаких лишних неминимальных), порядки 2, 2, 3, 3 —
и первым идёт самое вероятное, `q² = 0,01`, что подтверждает сортировку из
`analysis.rs`.

Пути проверяются отдельно: тоже четыре набора, у наборов порядка 2 вероятность
`(1−q)² = 0,81`. Это сквозная проверка механизма двойственности из
[`model.rs`](core-model-rs.md).

### `shared_event_exact_probability` — ловушка независимости

Тот самый пример, что и во [вводной главе](00-concepts.md):

```
(a & b) | (b & c),   q = 0,1
```

```rust
assert!((r.results[0].top_probability - 0.019).abs() < 1e-15);
```

Событие `b` общее, поэтому декомпозиция здесь **не сработает** (см.
`shared_event_blocks_modules` в [`module.rs`](core-module-rs.md)), и вся работа
ложится на BDD. Наивное «перемножить как независимые» дало бы 0,0199. Тест
подтверждает, что движок даёт 0,019 — точное значение.

Это самый важный тест на корректность во всём файле: он проверяет, что движок
не жульничает там, где жульничать удобно.

### `two_of_three_exponential` — мажоритарная схема

Три блока с λ = 1e-4, элемент «2 из 3», t = 1000 ч. Ожидание вычисляется в
самом тесте:

```rust
let q: f64 = 1.0 - (-0.1f64).exp();          // 0,0951626
let expect = 3.0 * q * q * (1.0 - q) + q * q * q;
```

Биномиальная формула «ровно два откажут» + «все три откажут». Здесь сходятся
две части движка: `dist.rs` даёт q(t), `bdd.rs` — конструкцию `atleast`.

### `markov_node_matches_exponential` — стыковка марковского узла

Двухсостоянийная марковская цепь `ok → fail` с интенсивностью 0,001 обязана
дать в точности то же, что экспонента с λ = 0,001. Тест ставит их в один
элемент И и ждёт `q²`:

```rust
assert!((r.results[0].top_probability - q * q).abs() < 1e-8);
```

Проверяется, что марковский узел действительно ведёт себя как обычное базовое
событие для всего остального движка.

### `sfc_mixed_conjunctive_disjunctive_arcs` — каноническая СФЦ

Фиктивный узел `t` имеет конъюнктивную дугу от `a` и две дизъюнктивные от `b`
и `c`. По формуле `y = x · K · D` при отсутствующем `x`:

```
y = a & (b | c)
```

При q = 0,1 (то есть p = 0,9 у каждого):

```
P = 0,9 × (1 − 0,1 × 0,1) = 0,9 × 0,99 = 0,891
```

```rust
assert!((r.results[0].top_probability - 0.891).abs() < 1e-12);
```

Сечения `a & (b|c)` суть `{a}` и `{b,c}` — порядки 1 и 2. Проверяется и это,
поскольку для СФЦ сечения получаются из **двойственной** функции, то есть
проверяется вся развилка «прямой/двойственный» из `analysis.rs`.

### `sfc_series_parallel` — СФЦ в старой нотации

Элементы 1 и 2 параллельно питают элемент 3, `combine: "or"` (то есть без
указания вида дуг). Тот же ответ 0,891, но записан через поле `combine`.

Этим фиксируется **обратная совместимость**: старые модели работают, и
проверка не декоративная — тест сломается, если ветку с `combine` уберут.

Дополнительно проверяется, что первое сечение — это `{n3}` с вероятностью 0,1:

```rust
assert_eq!(cuts.sets[0].events, vec!["n3".to_string()]);
```

Проверяется не только вероятность, но и **имя** — то есть сквозной путь
`EventId → sys.events[e].name → JSON`.

### `semi_markov_weibull_transition` — полумарковский путь через весь конвейер

Один вейбулловский переход должен воспроизвести функцию распределения
Вейбулла:

```
q(700) = 1 − e^(−0,49) = 0,38737
```

с допуском `2e-3` — потому что решатель численный, а не аналитический. Допуск
подобран так, чтобы быть в разы меньше любой физически значимой разницы, но
терпеть погрешность дискретизации.

### `semi_markov_repair_lowers_failure` — тест-неравенство

Замкнутого решения для «отказ по Вейбуллу + экспоненциальный ремонт» нет.
Поэтому проверяется свойство:

```rust
assert!(with_repair < no_repair);
assert!((0.0..=1.0).contains(&with_repair));
```

Ремонт может только уменьшить вероятность отказа, а результат обязан оставаться
вероятностью. Второе утверждение поймало бы численную расходимость решателя.

Приём с построением JSON форматированием строки позволяет сравнить две модели,
отличающиеся ровно одним переходом.

### `modular_decomposition_is_exact` — центральный тест на декомпозицию

Схема с двумя независимыми модулями:

```
m1 = a & b
m2 = d | e
m3 = c & m2
top = m1 | m3
```

Ожидание считается вручную, ровно тем же способом, каким работает движок:

```rust
let p_m1 = 0.2 * 0.3;                          // 0,06
let p_m2 = 1.0 - (1.0 - 0.4) * (1.0 - 0.25);   // 0,55
let p_m3 = 0.1 * p_m2;                         // 0,055
let expect = p_m1 + p_m3 - p_m1 * p_m3;        // 0,11170
assert!((r.results[0].top_probability - expect).abs() < 1e-15);
assert!(r.stats.modules >= 3);
```

Два утверждения, и оба нужны:

1. Ответ **точен** до `1e-15` — декомпозиция не вносит погрешности.
2. Модулей нашлось не менее трёх — декомпозиция действительно **сработала**.

Без второго теста алгоритм декомпозиции мог бы молча деградировать до «всё
одним куском»: ответ остался бы верным, а производительность рухнула бы,
и никто бы не заметил. Проверка `stats` — это тест на производительность,
выраженный через структуру.

### `multiple_times` — несколько моментов времени

`"times": [0, 100, 1000]` даёт три результата. При t = 0 вероятность нулевая
(ничего не успело отказать), при t = 100 — `1 − e^(−1)`.

Проверка `t = 0` полезнее, чем кажется: она ловит ошибки на границе в
`dist.rs` (`if t <= 0.0`) и в марковских решателях.

### `editor_layout_field_is_ignored` — файл редактора считается движком

Веб-редактор сохраняет схему как обычный запрос плюс поле `layout` с
координатами узлов (и состояний марковских узлов). Тест берёт схему из
`sfc_series_parallel`, добавляет к ней `layout` и проверяет, что ответ прежний —
0,891.

Тест защищает **договорённость**, а не вычисление: serde пропускает незнакомые
поля, пока над структурой нет `#[serde(deny_unknown_fields)]`. Стоит кому-то
её добавить — сохранённые из браузера файлы перестанут считаться через CLI, и
сломается именно этот тест, а не пользовательские файлы.

## Как это читать

Файл — по сути формальная спецификация движка:

| Свойство | Тест |
|---|---|
| Вероятность точна при общих событиях | `shared_event_exact_probability` |
| Вероятность точна на неприводимой (мостиковой) схеме | `bridge_fault_tree` |
| Декомпозиция не портит ответ и при этом работает | `modular_decomposition_is_exact` |
| Двойственность даёт верные пути | `bridge_fault_tree`, `sfc_series_parallel` |
| Обе нотации дают согласованные результаты | `sfc_*` |
| Марковские узлы стыкуются с логическим слоем | `markov_node_matches_exponential` |
| Полумарковский решатель численно верен | `semi_markov_*` |
| Старый формат продолжает работать | `sfc_series_parallel` |
| Файлы редактора (с `layout`) принимаются движком | `editor_layout_field_is_ignored` |

Запуск:

```
cargo test                       # всё
cargo test --test integration    # только этот файл
cargo test bridge                # один тест по подстроке имени
```
