# 10. `crates/cra-cli/src/main.rs` — программа командной строки

**Размер:** 96 строк. **Задача:** прочитать JSON-запрос из файла или со stdin,
посчитать, вывести JSON-ответ.

## Какую задачу решает

Движок — библиотека, а библиотеку нельзя запустить. Этот файл — самая тонкая
из возможных оболочек, делающая его исполняемой программой:

```
cra <input.json | -> [-o out.json] [--pretty]
```

Три сценария использования:

1. **Ручная проверка.** Написал модель, запустил, посмотрел числа.
2. **Скрипты.** Расчёт в конвейере: `cat model.json | cra - | jq .results`.
3. **Мост для другого фронтенда.** Программа на C++/Qt может запустить `cra`
   через `QProcess`, отдать JSON в stdin и прочитать ответ из stdout. Не нужен
   ни C ABI, ни привязка к Rust — просто два потока текста. Это прямо указано
   в шапке файла.

## Разбор аргументов вручную

```rust
let mut args = std::env::args().skip(1);
while let Some(a) = args.next() {
    match a.as_str() {
        "-o" | "--output" => { output = args.next(); … }
        "--pretty" => pretty = true,
        "-h" | "--help" => { print_usage(); return; }
        _ if input.is_none() => input = Some(a),
        _ => { eprintln!("error: unexpected argument '{a}'"); std::process::exit(2); }
    }
}
```

Ни `clap`, ни `structopt`, ни какой-либо другой библиотеки разбора аргументов.
Причина — общая для всего проекта: на Astra Linux каждая зависимость должна
быть завендорена, проверена и обоснована. Ради трёх флагов это не стоит того.
Двадцать строк ручного разбора делают то же самое и полностью прозрачны для
аудита.

Заметьте порядок ветвей в `match`: `_ if input.is_none()` идёт **после**
именованных флагов, поэтому первый непонятный аргумент считается именем входного
файла, а второй — уже ошибкой.

## Ввод: файл или stdin

```rust
let text = if input == "-" {
    let mut s = String::new();
    std::io::stdin().read_to_string(&mut s)?;
    s
} else {
    std::fs::read_to_string(&input)?
};
```

Соглашение `-` = стандартный ввод — общепринятое в Unix (так делают `cat`,
`tar`, `gpg`). Именно оно позволяет работать в конвейере и через `QProcess`.

## Расчёт

```rust
let req: cra::Request = serde_json::from_str(&text)?;
let resp = cra::analyze_request(&req)?;
```

Две строки. Всё остальное в файле — обработка ошибок и ввод-вывод.

## Коды возврата

Продумано, а не случайно:

| Код | Значение |
|---|---|
| 0 | успех |
| 1 | ошибка выполнения: файл не читается, JSON неверен, модель отвергнута движком |
| 2 | ошибка употребления: нет аргументов, неизвестный флаг |

Это стандартное соглашение Unix, и оно позволяет вызывающему скрипту различать
«я неправильно позвал программу» и «программа не смогла сделать работу».
Сообщения об ошибках идут в **stderr**, результат — в **stdout**, поэтому
`cra model.json > out.json` даёт чистый JSON даже при наличии диагностики.

## Вывод

```rust
let out = if pretty { serde_json::to_string_pretty(&resp) }
          else      { serde_json::to_string(&resp) }
          .expect("response serialization cannot fail");
```

Комментарий `"response serialization cannot fail"` объясняет, почему здесь
допустим `expect` (то есть паника при ошибке): `Response` состоит из чисел,
строк и векторов, а сериализация таких данных в JSON не может провалиться. Это
не ленивая обработка ошибок, а обоснованное утверждение.

При `-o` результат пишется в файл, иначе — в stdout.

# Примеры моделей

Два файла в `crates/cra-cli/examples/` служат сразу трём целям: примеры для
пользователя, встроенные примеры в веб-интерфейсе (`assets.rs` включает их в
бинарник через `include_str!`) и тестовые данные.

## `fault_tree.json` — реалистичная схема

```
system_failure = ИЛИ(hydraulics, sensors, power)
   hydraulics  = ИЛИ(pumps, valve)
      pumps    = И(pump_a, pump_b)          два насоса, резервирование
      valve    = Вейбулл (износ)
   sensors     = 2 из 3                     мажоритарная схема
   power       = марковская цепь из 3 состояний
```

Здесь намеренно собраны почти все возможности движка:

| Элемент | Что демонстрирует |
|---|---|
| `pump_a` | экспонента, λ = 1e-4 |
| `pump_b` | экспонента **с ремонтом**, μ = 1e-1 |
| `valve` | Вейбулл, форма 2 (износ) |
| `sensor1..3` | постоянное q = 0,01 |
| `power` | марковская цепь: номинал → деградация → потеря, с восстановлением |
| `pumps` | элемент И (резервирование) |
| `sensors` | «2 из 3» |
| `times` | три момента: 1000, 5000, 10000 |
| `max_order: 6` | ограничение размера сечений |

Расчёт для нескольких моментов времени показывает, как разные механизмы
отказов проявляются по-разному: экспоненциальные насосы дают почти линейный
рост в начале, вейбулловская задвижка почти не даёт вклада на 1000 ч, но
заметно растёт к 10000 ч.

Марковский узел `power` стоит рассмотреть отдельно:

```json
{"from": "nominal",  "to": "degraded", "rate": 2e-4},
{"from": "degraded", "to": "nominal",  "rate": 5e-2},    ← восстановление
{"from": "degraded", "to": "lost",     "rate": 1e-3},
{"from": "nominal",  "to": "lost",     "rate": 1e-6}     ← прямой отказ
```

Такое не выразить одним распределением: система может деградировать и
восстановиться, а может и отказать напрямую. Ради подобных случаев
`markov.rs` и существует.

## `sfc_bridge.json` — мостиковая схема в нотации СФЦ

Та же мостиковая схема, что и в интеграционном тесте, но записанная как схема
функциональной целостности:

```
        left1 ─────────► right1 ─┐
      ╱   │                ▲      │
   src    │ bridge ────────┤      ├─► sink
      ╲   ▼                ▼      │
        left2 ─────────► right2 ─┘
```

Особенности записи:

- у `src` стоит `q: 0.0` — идеальный источник, полезный приём для задания
  входа схемы;
- `sink` — **фиктивный узел**: у него нет поля `dist`, только входы. Он не
  элемент, а точка сбора логики;
- `"mission_time": 0` — время не важно, потому что все распределения
  постоянные.

Полезно запустить оба примера и сравнить вывод:

```
cargo run --bin cra -- crates/cra-cli/examples/fault_tree.json --pretty
cargo run --bin cra -- crates/cra-cli/examples/sfc_bridge.json --pretty
```

У первого `interpretation` будет «P(top event / failure)», у второго —
«P(criterion is satisfied)». Одно и то же поле `top_probability`, но
противоположный смысл — это и есть работа флага `ModelKind` из
[`model.rs`](core-model-rs.md).
