# 14. `crates/cra-server/src/server.rs` — приём связей и пул потоков

**Размер:** 122 строки. **Задача:** слушать TCP-порт, раздавать входящие связи
рабочим потокам, отвергать перегрузку.

## Какую задачу решает

Одновременно могут прийти несколько инженеров. Расчёт нагружает процессор и
может занимать секунды. Нужна модель параллелизма, которая:

- использует все ядра;
- не создаёт по потоку на связь (10 000 связей = 10 000 потоков = смерть);
- при перегрузке отвечает внятно, а не падает.

## Выбранная модель: пул потоков и общая очередь

```rust
let (tx, rx): (Sender<TcpStream>, Receiver<TcpStream>) = mpsc::channel();
let rx = Arc::new(Mutex::new(rx));

for _ in 0..cfg.workers {
    workers.push(thread::spawn(move || loop {
        let stream = {
            let guard = rx.lock().unwrap_or_else(|e| e.into_inner());
            guard.recv()
        };
        match stream {
            Ok(stream) => { handle_connection(stream, &cfg); inflight.fetch_sub(1, …); }
            Err(_) => break,   // канал закрыт — завершаемся
        }
    }));
}
```

Схема классическая: N рабочих потоков разбирают связи из одной очереди.

`mpsc` в Rust — это «много отправителей, один получатель», то есть получатель
по умолчанию не разделяется. Обёртка `Arc<Mutex<Receiver>>` превращает канал в
«много получателей»: потоки по очереди берут замок и вытаскивают следующую
связь.

Существенная деталь области видимости:

```rust
let stream = {
    let guard = rx.lock()…;
    guard.recv()
};                          // ← замок отпущен ЗДЕСЬ
handle_connection(stream, &cfg);   // расчёт идёт БЕЗ замка
```

Замок держится ровно на время взятия связи из очереди — микросекунды. Расчёт,
который может длиться секунды, выполняется уже без замка. Если бы `guard`
жил до конца итерации цикла, все потоки выстроились бы в очередь за одним
замком, и параллелизма не было бы вовсе.

### `unwrap_or_else(|e| e.into_inner())`

```rust
rx.lock().unwrap_or_else(|e| e.into_inner())
```

В Rust мьютекс «отравляется», если поток паниковал, держа его. По умолчанию
все последующие `lock()` возвращают ошибку — предполагается, что данные могли
остаться в несогласованном состоянии.

Здесь под замком лежит приёмник канала, у которого нет собственных инвариантов
для порчи. Поэтому `into_inner()` берёт данные всё равно. Без этого одна
паника в одном обработчике навсегда парализовала бы весь сервер — отказ куда
хуже исходной проблемы.

## Ограничение нагрузки

```rust
let inflight = Arc::new(AtomicUsize::new(0));

for incoming in listener.incoming() {
    let current = inflight.fetch_add(1, Ordering::AcqRel) + 1;
    if current > cfg.max_connections {
        inflight.fetch_sub(1, Ordering::AcqRel);
        reject_overloaded(stream);
        continue;
    }
    if tx.send(stream).is_err() { break; }
}
```

Атомарный счётчик отслеживает число связей «в работе». Сверх предела связь
немедленно получает 503:

```rust
fn reject_overloaded(mut stream: TcpStream) {
    audit::log(&AuditRecord { event: "rejected", …, status: 503,
                              detail: "connection limit reached" });
    let _ = Response::error(503, "server busy").write(&mut stream, false);
}
```

Два свойства делают это правильным поведением, а не грубым:

1. **Отказ вежливый.** Клиент получает настоящий HTTP-ответ 503 и понимает, что
   произошло, — вместо оборванной связи или бесконечного ожидания.
2. **Отказ записан в журнал.** Всплеск событий `rejected` в journald — это
   готовый сигнал для мониторинга: сервер под нагрузкой.

`fetch_add` возвращает **предыдущее** значение, поэтому текущее — это
`+ 1`. `Ordering::AcqRel` — модель памяти, обеспечивающая согласованную
видимость счётчика между потоками.

Счётчик уменьшается в рабочем потоке **после** обработки связи, поэтому предел
считает связи в обработке, а не суммарно принятые.

## Обработка одной связи

```rust
fn handle_connection(stream: TcpStream, cfg: &Config) {
    let peer_ip = match stream.peer_addr() { Ok(a) => a.ip(), Err(_) => return };
    if cfg.request_timeout_secs > 0 {
        let d = Some(Duration::from_secs(cfg.request_timeout_secs));
        let _ = stream.set_read_timeout(d);
        let _ = stream.set_write_timeout(d);
    }
    let _ = stream.set_nodelay(true);
    …
}
```

**Таймауты** обязательны. Без них клиент, открывший связь и не приславший
ничего, занимал бы рабочий поток вечно (атака Slowloris). При 8 потоках
достаточно восьми таких клиентов, чтобы полностью остановить сервер.

**`set_nodelay(true)`** отключает алгоритм Нейгла — тот копит мелкие пакеты
перед отправкой, чтобы эффективнее использовать сеть. Для запрос-ответного
протокола это добавляет до 40 мс задержки без всякой пользы.

`peer_addr()` берётся **до** любого чтения, потому что после сбоя связи адрес
уже не получить, а он нужен для журнала и для проверки доверенного прокси.

### Одна связь — один запрос

```rust
// Один запрос на связь (Connection: close). Так проще и надёжнее; для
// внутреннего инструмента этого достаточно.
```

Keep-alive не поддерживается: `resp.write(&mut stream_out, false)` всегда
передаёт `keep_alive = false`, значит в ответе стоит `Connection: close`.

Компромисс осознанный. Keep-alive потребовал бы отслеживания состояния связи,
таймаутов простоя, обработки конвейеризации запросов — то есть заметного
усложнения и новых поверхностей атаки. Веб-интерфейс делает единицы запросов
за сеанс, накладные расходы на новую TCP-связь несущественны, а вот
поддерживаемый прокси спереди (nginx) держит keep-alive к клиенту сам:

```
upstream cra_backend {
    server 127.0.0.1:8080;
    keepalive 16;
}
```

## Завершение работы

```rust
drop(tx);
for w in workers { let _ = w.join(); }
```

Когда цикл приёма заканчивается, отправитель уничтожается; рабочие потоки
получают из `recv()` ошибку «канал закрыт» и выходят из цикла. Затем `join()`
дожидается завершения каждого — то есть текущие расчёты доводятся до конца,
а не обрываются на середине.

## Стартовое сообщение

```rust
eprintln!("cra-server listening on http://{local} · workers={} · auth={} · max_conn={}",
          cfg.workers, cfg.auth_summary(), cfg.max_connections);
eprintln!("note: serve behind a certified ГОСТ-TLS terminating proxy; \
           do not expose plain HTTP outside a trusted segment");
```

Печатается фактически занятый адрес (`listener.local_addr()`), а не
запрошенный, — это важно, когда указан порт `0` и система выбрала свободный
(так делают тесты).

Предупреждение о TLS выводится при **каждом** запуске. Оно попадает в journald
и оказывается на виду у администратора, а не только в документации, которую
можно не прочесть.
